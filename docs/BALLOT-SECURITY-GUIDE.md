## 1. ปัญหาที่แก้

ระบบเลือกตั้งต้องทำสองอย่างที่ขัดกันเองให้ได้พร้อมกัน

- **ต้องรู้** ว่าแต่ละพรรคได้กี่คะแนน ไม่งั้นประกาศผลไม่ได้
- **ต้องไม่รู้** ว่าใครเลือกใคร และต้องไม่ใช่แค่ "ไม่แสดงบนหน้าเว็บ" แต่ต้องพิสูจน์ไม่ได้จริง ๆ
  แม้แต่กับคนที่ถือฐานข้อมูลทั้งก้อนไปเปิดดูเอง

ของเดิมทำไม่ได้ เพราะเก็บตัวเลือกไว้ในตารางผู้ใช้ตรง ๆ ใครเปิดฐานข้อมูลได้ก็เห็นหมดทันที

ของปัจจุบันแยกเป็นสองส่วนที่ไม่ต่อกัน

| เก็บอะไร | อยู่ที่ไหน | มีอะไรบ้าง |
|---|---|---|
| **คะแนนรวม** | `Candidate.score` | ตัวเลขอย่างเดียว บวกทีละหนึ่งตอนมีคนโหวต · นี่คือผลที่ประกาศ |
| **ตัวบัตร** | ตาราง `Ballot` | ตัวเลือกที่เข้ารหัสไว้ · **ไม่มีรหัสนักศึกษา ไม่มีเวลาละเอียด** เก็บแค่ระดับชั่วโมง |

ตารางผู้ใช้รู้แค่ว่า "คนนี้ใช้สิทธิ์ไปแล้ว" ไม่รู้ว่าเลือกอะไร · ตารางบัตรรู้ว่ามีคนเลือกอะไรบ้าง
แต่ไม่รู้ว่าใคร · **ไม่มีคอลัมน์ไหนในระบบที่เชื่อมสองตารางนี้เข้าหากัน** ไม่ใช่เพราะลบทิ้ง
แต่เพราะไม่เคยมี

> คะแนนที่ประกาศไม่ได้มาจากการถอดบัตร แต่มาจาก `Candidate.score` ที่นับไปตั้งแต่ตอนโหวต
> การถอดบัตรใช้เฉพาะตอนมีข้อพิพาทเท่านั้น — เพราะฉะนั้น **กุญแจถอดบัตรหาย ไม่ทำให้ผลเลือกตั้งเสีย**

## 2. กุญแจ 3 ดอก

พิธีสร้างกุญแจ (`node scripts/generate-election-keys.js`) ให้ของมา 3 ชิ้น คนละหน้าที่กันหมด

| ดอก | เก็บที่ไหน | ใช้ตอนไหน | หายแล้วเสียอะไร | หลุดแล้วเสียอะไร |
|---|---|---|---|---|
| **PUBLIC KEY** | env `ELECTION_BALLOT_PUBLIC_KEY` บนเซิร์ฟเวอร์ | ทุกครั้งที่มีคนกดโหวต | โหวตไม่ได้ทั้งระบบ (503) | ไม่เสียหาย เป็นของเปิดเผยโดยธรรมชาติ |
| **PRIVATE KEY** | ไฟล์เข้ารหัส `key-<ปี>.enc` เก็บ 2 ที่ **นอกเซิร์ฟเวอร์** | เฉพาะตอนมีข้อพิพาทต้องนับซ้ำ | นับซ้ำไม่ได้ · **ผลเลือกตั้งไม่เสีย** | **ร้ายแรงที่สุด** — ดู [§3](#3-เหตุผลข้อเดียวที่สำคัญที่สุด) |
| **CHAIN SECRET** | env `BALLOT_CHAIN_SECRET` บนเซิร์ฟเวอร์ **+ สำเนานอกเครื่อง** | ตรวจว่าบัตรถูกแก้หรือไม่ | ตรวจโซ่ไม่ได้อีกเลย บัตรยังอยู่ครบแต่พิสูจน์ไม่ได้ | คนที่เข้าถึงฐานข้อมูลระดับ superuser ได้ จะแก้บัตรแล้วเขียนโซ่ใหม่ให้เนียนได้ |

### สามอย่างที่ห้ามทำ

- **ห้ามเอา private key ขึ้นเซิร์ฟเวอร์** ไม่ว่ากรณีใด รวมถึงเอาไปวางชั่วคราวแล้วตั้งใจลบทีหลัง
- **ห้ามเก็บ private key ไว้ในชุดสำรองเดียวกับฐานข้อมูล** — สำรองชุดเดียวหลุด ได้ครบทั้งคู่
- **ห้ามสร้างกุญแจใหม่ระหว่างหีบเปิดอยู่** บัตรที่ลงไปแล้วจะถอดไม่ออกตลอดกาล และโซ่จะขาด

### เซิร์ฟเวอร์ต้องมีอะไรบ้าง

มีแค่ **public key + chain secret** เท่านั้น · ถ้าขาดตัวใดตัวหนึ่ง `/api/vote` จะปฏิเสธการโหวต
ทันที (คืน 503) และ**ไม่เก็บตัวเลือกแบบไม่เข้ารหัสเป็นทางออกสำรอง** — ตั้งใจให้พังแบบปิดสนิท
ดีกว่าเก็บบัตรที่อ่านออกไว้โดยไม่มีใครรู้

## 3. เหตุผลข้อเดียวที่สำคัญที่สุด

**ทำไม private key ห้ามอยู่บนเซิร์ฟเวอร์**

ถอดบัตรอย่างเดียวไม่ได้ทำให้รู้ว่าใครเลือกใคร เพราะบัตรไม่มีชื่อคนโหวตอยู่แล้ว ถอดออกมา
ก็ได้แค่ "กองตัวเลือก" ซึ่งก็คือผลที่ประกาศไปแล้ว

อันตรายอยู่ที่**การจับคู่** — บัตรเรียงตามลำดับที่ลง (`seq`) และตารางผู้ใช้เก็บเวลาที่แต่ละคน
กดใช้สิทธิ์ไว้ (`votedAt`) ใครที่ถือ **ทั้งสำเนาฐานข้อมูลและ private key** พร้อมกัน จะเอาสองอย่างนี้
มาเรียงทาบกันแล้วไล่ได้ว่าใบไหนของใคร

แปลว่าความลับของการลงคะแนนไม่ได้อยู่ที่การเข้ารหัส แต่อยู่ที่**การแยกกุญแจออกจากที่ที่เก็บข้อมูล**
ตราบใดที่สองอย่างนี้ไม่เคยอยู่ในมือคนเดียวกัน ต่อให้ฐานข้อมูลทั้งก้อนหลุด ก็ยังไล่ไม่ได้ว่าใครเลือกอะไร

### ตอนนี้คณะเก็บกุญแจแบบคนเดียวถือ

**ปัจจุบันเจ้าหน้าที่ IT ถือทั้งไฟล์และรหัสผ่านเอง** ไม่ได้แบ่งให้ใครถือคนละส่วน
เขียนไว้ตรงนี้เพื่อให้คนที่มารับช่วงต่อรู้ว่าระบบกันอะไรได้จริงและกันอะไรไม่ได้

| กันได้ | กันไม่ได้ |
|---|---|
| คนนอกที่ยึดเซิร์ฟเวอร์ไปทั้งเครื่อง — ไม่มีกุญแจก็ถอดบัตรไม่ได้ | เจ้าหน้าที่ IT เอง — เข้าถึงได้ทั้งฐานข้อมูลและกุญแจ จึงจับคู่ได้ในทางเทคนิค |
| คนที่ได้ชุดสำรองฐานข้อมูลไป — กุญแจไม่ได้อยู่ในนั้น | คนที่ได้ทั้งไฟล์ `.enc` และรหัสผ่านไปพร้อมกัน |
| การแก้บัตรย้อนหลัง — โซ่ยังตรวจจับได้เหมือนเดิม | |

แปลว่าความลับของผู้ลงคะแนน ณ ตอนนี้ตั้งอยู่บน**ความไว้ใจในตัวเจ้าหน้าที่** ไม่ใช่บนโครงสร้าง
ที่บังคับ · เป็นข้อตกลงที่หน่วยงานขนาดเล็กเลือกกันได้ตามปกติ แต่ต้องเป็นการเลือกที่รู้ตัว
ไม่ใช่เผลอเป็นไปเอง

**ถ้าวันหนึ่งคณะอยากให้เป็นโครงสร้างจริง** ทำได้ทันทีโดยไม่ต้องแก้โค้ดอะไรเลย — ให้ไฟล์ `.enc`
กับคนหนึ่ง บอกรหัสผ่านอีกคนหนึ่ง คนเดียวเปิดไม่ได้ ต้องมาเจอกันถึงจะเปิดได้ ได้ผลเท่าซองปิดผนึก
สองซองแต่ไม่มีกระดาษให้หาย · คนที่สองควรเป็นเจ้าหน้าที่ประจำ ไม่ใช่นักศึกษา เพราะกุญแจต้องอยู่
ได้นานกว่าวาระของสโมสรฯ

### สิ่งที่ทำได้ทันทีแม้ถือคนเดียว

- **เก็บรหัสผ่านในตัวจัดการรหัสผ่านของคณะ ไม่ใช่ของส่วนตัว** — ถ้าเจ้าหน้าที่ลาออกกะทันหัน คณะยังเปิดได้
- **ทำลายกุญแจให้ตรงเวลาตาม [§6](#6-อายุของกุญแจ)** — ยิ่งเก็บสั้น ช่วงที่มีความเสี่ยงยิ่งสั้น
- **กรอกใบบันทึกใน [§7](#7-ใบบันทึกผู้ถือกุญแจ) ทุกปี** — ให้เป็นสถานะที่มีคนรู้ ไม่ใช่เรื่องที่ไม่มีใครเคยถาม

## 4. โซ่บัตร

การเข้ารหัสกันคนอ่าน แต่ไม่ได้กันคนแก้ · โซ่บัตรคือส่วนที่กันการแก้

บัตรทุกใบเก็บลายนิ้วมือของใบก่อนหน้าไว้ด้วย ใบที่ 2 อ้างถึงใบที่ 1 · ใบที่ 3 อ้างถึงใบที่ 2
ต่อกันไปเรื่อย ๆ ทั้งเส้น ถ้ามีคนไปแก้ใบใดใบหนึ่งกลางทาง ลายนิ้วมือของใบนั้นเปลี่ยน ทำให้ใบถัดไป
ที่อ้างถึงมันผิดไปด้วย และผิดต่อกันเป็นทอด ๆ จนสุดเส้น **แก้ใบเดียวก็รู้ทันทีว่ามีการแก้**

```bash
node scripts/verify-ballot-chain.js     # ตรวจทั้งเส้น + นับจำนวนใบ
```

รันก่อนให้สโมสรฯ ประกาศผลทุกครั้ง · ถ้าผ่าน แปลว่าบัตรทุกใบยังเป็นชุดเดิมที่ลงไปตอนโหวต

### ทำไมต้อง export ปลายโซ่ออกไปเก็บข้างนอกด้วย

คนที่มีทั้ง chain secret และสิทธิ์ superuser ในฐานข้อมูล สามารถแก้บัตรแล้วเขียนโซ่ใหม่
ทั้งเส้นให้ต่อกันเนียนได้ — โซ่ที่ตรวจตัวเองจึงยังไม่พอ

```bash
node scripts/export-chain-head.js       # ตั้ง cron เก็บปลายโซ่ไว้นอกฐานข้อมูลเป็นระยะ
```

ถ้าปลายโซ่วันนี้ไม่ตรงกับที่ export ไว้เมื่อวาน แปลว่ามีคนเขียนใหม่ · การจะแก้บัตรแบบไม่ถูกจับ
จึงต้องได้ทั้ง chain secret **และ** superuser **และ** ต้องย้อนไปแก้ไฟล์ที่ export ออกไปแล้วทุกชุด
ซึ่งอยู่คนละที่กัน

> **บัญชีของเว็บอ่านและเพิ่มบัตรได้ แต่แก้และลบไม่ได้** (`SELECT, INSERT` เท่านั้น) — บังคับที่ระดับฐานข้อมูลด้วย
> `scripts/sql/ballot-grants.sql` ต้อง apply บน production เสมอ ต่อให้ตัวเว็บถูกเจาะ
> ก็ยังแก้บัตรย้อนหลังไม่ได้

## 5. ปฏิทินต่อปี

| เมื่อไหร่ | ทำอะไร | ใคร |
|---|---|---|
| ก่อนเปิดหีบ | พิธีสร้างกุญแจบนเครื่อง offline · ใส่ public key + chain secret ลง env | IT |
| ก่อนเปิดหีบ | apply `scripts/sql/ballot-grants.sql` · `npm run preflight` ต้องผ่าน | IT |
| ระหว่างเปิดหีบ | cron `export-chain-head.js` เก็บปลายโซ่ | IT |
| ปิดหีบแล้ว ก่อนประกาศ | `verify-ballot-chain.js` แล้วตามด้วย `reconcile-scores.js` | IT |
| ขึ้นปีใหม่ | สร้างกุญแจชุดใหม่ · จัดการกุญแจปีเก่าตาม [§6](#6-อายุของกุญแจ) | IT |

**กุญแจชุดใหม่ทุกปี ไม่ใช้ซ้ำ** — ปีการเลือกตั้งจบแล้วกุญแจชุดนั้นก็หมดหน้าที่

## 6. อายุของกุญแจ

> ⚠️ **ข้อนี้รอเจ้าของระบบยืนยัน** ค่าที่เขียนไว้ข้างล่างคือข้อเสนอที่สอดคล้องกับนโยบายสำรองข้อมูล
> ที่ใช้อยู่แล้วใน `docs/STAFF-IT-GUIDE.md` §5 — ถ้าตกลงตามนี้ให้ลบกล่องนี้ทิ้ง

**กฎข้อเดียว: กุญแจมีอายุเท่ากับชุดสำรองที่มันเปิดได้**

คู่มือ IT กำหนดให้เก็บไฟล์สำรองของปีเก่าไว้อย่างน้อยหนึ่งปี เพราะบัตรที่ลบแล้วนับใหม่ไม่ได้อีก
กุญแจก็ต้องอยู่ครบช่วงนั้นเหมือนกัน ไม่งั้นเก็บบัตรไว้ก็เปล่าประโยชน์

| ของ | เก็บถึงเมื่อไหร่ |
|---|---|
| ไฟล์ `key-<ปี>.enc` | จนกว่าการเลือกตั้งปีถัดไปจะรับรองผลเสร็จ แล้วทำลาย |
| สำเนา chain secret ของปีนั้น | ทำลายพร้อมกัน |
| ชุดสำรองฐานข้อมูลของปีนั้น | ทำลายพร้อมกัน |

**ทำลายทั้งสามอย่างพร้อมกันเสมอ** อย่าทำลายอย่างเดียวแล้วเหลืออีกอย่าง — เหลือกุญแจไว้โดยไม่มีบัตร
คือเก็บความเสี่ยงไว้เปล่า ๆ เหลือบัตรไว้โดยไม่มีกุญแจคือเก็บของที่ใช้อะไรไม่ได้

ถ้าไม่กำหนดข้อนี้ไว้ สิ่งที่จะเกิดขึ้นจริงคือกุญแจของทุกปีกองสะสมกันไปเรื่อย ๆ และภายในสามสี่ปี
ก็จะไม่มีใครรู้ว่ามีกี่ชุด อยู่กับใครบ้าง

## 7. ใบบันทึกผู้ถือกุญแจ

ปรินต์ กรอก เซ็น เก็บไว้กับเอกสารการเลือกตั้งของปีนั้น · **ข้อนี้สำคัญกว่าที่คิด** เพราะภายในสองสามปี
คนที่อยู่ในพิธีจะย้ายงานหรือจบไปหมด และไม่มีใครในระบบจำได้ว่ากุญแจอยู่ไหน

> เมื่อผู้ถือพ้นหน้าที่ ให้สร้างกุญแจชุดใหม่และทำลายชุดเก่า — ง่ายและปลอดภัยกว่าการส่งต่อ

## 8. เกิดเหตุ

| อาการ | ทำทันที |
|---|---|
| **โหวตไม่ได้ทั้งระบบ ขึ้น 503** ทั้งที่ยังไม่ถึงเวลาปิด | env กุญแจไม่ครบ → `sh scripts/setup.sh --check` · ใส่ค่าให้ครบแล้วรีสตาร์ท · **ห้ามสร้างกุญแจใหม่** ถ้ามีบัตรลงไปแล้ว |
| **สงสัยว่าไฟล์กุญแจหลุด** ระหว่างหีบเปิด | ให้สโมสรฯ สลับโหมด `PAUSE` ก่อน · แจ้งกรรมการและหัวหน้างานทันที · **ห้ามสร้างกุญแจใหม่ทับ** บัตรเดิมจะถอดไม่ออก · เป็นการตัดสินใจของกรรมการว่าจะเดินต่อหรือเริ่มใหม่ ไม่ใช่ของ IT |
| **สงสัยว่าไฟล์กุญแจหลุด** หลังรับรองผลแล้ว | ผลไม่เสีย แต่ความลับของผู้ลงคะแนนเสี่ยง ถ้าคนนั้นได้สำเนาฐานข้อมูลไปด้วย → ทำลายชุดสำรองของปีนั้นตาม [§6](#6-อายุของกุญแจ) ให้เร็วขึ้น แล้วบันทึกเหตุการณ์ไว้ |
| **`verify-ballot-chain.js` บอกว่าโซ่ขาด** | **อย่าเพิ่งประกาศผล** · เทียบปลายโซ่กับไฟล์ที่ export ไว้ก่อนหน้า เพื่อดูว่าขาดตั้งแต่ใบไหน · เก็บ log ไว้ · แจ้งกรรมการ — เป็นเรื่องระดับที่กรรมการต้องตัดสิน |
| **เผลอสร้างกุญแจใหม่ทับตอนหีบเปิดอยู่** | หยุดระบบทันที · ถ้ายังมี env ชุดเก่าอยู่ในไฟล์สำรองหรือ scrollback ให้กู้กลับมาก่อนสิ่งอื่นใด · บัตรที่ลงด้วยกุญแจเก่าจะถอดไม่ออกถ้าหาชุดเก่าไม่เจอ (คะแนนรวมยังอยู่ครบ) |
| **ลืมรหัสผ่านของไฟล์ `.enc`** | เปิดไม่ได้อีกเลย ไม่มีทางกู้ · เสียแค่ความสามารถในการนับซ้ำ ผลไม่เสีย · สร้างชุดใหม่ในปีถัดไปและบันทึกรหัสให้ดีขึ้น |

### ถ้าต้องนับซ้ำจริง

ทำบนเครื่อง offline เท่านั้น **ต้องมีกรรมการอยู่ด้วยเป็นพยาน** — ยิ่งกุญแจอยู่กับคนเดียว
การมีพยานยิ่งสำคัญ เพราะเป็นสิ่งเดียวที่ยืนยันได้ว่าการเปิดบัตรครั้งนี้ทำต่อหน้าคนอื่น

```bash
# 1. เปิดไฟล์กุญแจ (ใช้ไฟล์ + รหัสผ่านที่ตั้งไว้ตอนพิธี)
node scripts/generate-election-keys.js --decrypt key-2569.enc

# 2. คัดลอกส่วน PRIVATE KEY ที่พิมพ์ออกมา บันทึกเป็นไฟล์ชั่วคราวนอกโปรเจกต์
#    เช่น /tmp/recount.pem

# 3. นับซ้ำ
node scripts/decrypt-recount.js --key /tmp/recount.pem

# 4. ลบไฟล์ชั่วคราวทิ้ง แล้วล้าง scrollback ปิดเทอร์มินัล
```

> **`--key` ต้องมี** ถ้าใส่ path เฉย ๆ สคริปต์จะไม่รับ · ข้อความท้ายผลลัพธ์ของ `--decrypt`
> เขียนตกไป ให้ยึดตามคำสั่งข้างบนนี้

ผลที่ได้คือจำนวนบัตรแยกรายพรรค เอาไปเทียบกับ `Candidate.score` ที่ประกาศไป
ถ้าตรงกันคือจบเรื่อง · ถ้าไม่ตรง ให้รัน `reconcile-scores.js` ประกอบ แล้วส่งทั้งสองผลให้กรรมการ
