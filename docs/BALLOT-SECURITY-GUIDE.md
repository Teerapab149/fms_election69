## 1. ปัญหาที่แก้

ระบบเลือกตั้งต้องทำสองอย่างที่ขัดกันเองให้ได้พร้อมกัน

- **ต้องรู้** ว่าแต่ละพรรคได้กี่คะแนน ไม่งั้นประกาศผลไม่ได้
- **ต้องไม่รู้** ว่าใครเลือกใคร และต้องไม่ใช่แค่ "ไม่แสดงบนหน้าเว็บ" แต่ต้องพิสูจน์ไม่ได้จริง ๆ
  แม้แต่กับคนที่ถือฐานข้อมูลทั้งก้อนไปเปิดดูเอง

ของเดิมทำไม่ได้ เพราะเก็บตัวเลือกไว้ในตารางผู้ใช้ตรง ๆ ใครเปิดฐานข้อมูลได้ก็เห็นหมดทันที

ของปัจจุบันแยกเป็นสองส่วนที่ไม่ต่อกัน

| เก็บอะไร | อยู่ที่ไหน | มีอะไรบ้าง |
|---|---|---|
| **คะแนนรวม** | `Candidate.score` | ตัวเลขอย่างเดียว บวกทีละหนึ่งตอนมีคนโหวต นี่คือผลที่ประกาศ |
| **ตัวบัตร** | ตาราง `Ballot` | ตัวเลือกที่เข้ารหัสไว้ **ไม่มีรหัสนักศึกษา ไม่มีเวลาละเอียด** เก็บแค่ระดับชั่วโมง |

ตารางผู้ใช้รู้แค่ว่า "คนนี้ใช้สิทธิ์ไปแล้ว" ไม่รู้ว่าเลือกอะไร ตารางบัตรรู้ว่ามีคนเลือกอะไรบ้าง
แต่ไม่รู้ว่าใคร **ไม่มีคอลัมน์ไหนในระบบที่เชื่อมสองตารางนี้เข้าหากัน** ไม่ใช่เพราะลบทิ้ง
แต่เพราะไม่เคยมี

มีข้อยกเว้นเชิงเทคนิคหนึ่งข้อที่ต้องรู้ คือตั้งแต่เปิดหีบจนถึงกดรับรองผล แถวผู้ใช้กับแถวบัตรของการโหวตครั้งเดียวกัน
มีค่า `xmin` (หมายเลข transaction ของ PostgreSQL) ตัวเดียวกัน คนที่อ่านทั้งสองตารางตรง ๆ บนฐานข้อมูลได้จึงจับคู่ได้ว่า
บัตรใบไหนเป็นของใคร แต่ยังไม่รู้ว่าเลือกอะไรถ้าไม่มี private key ตอนรับรองผลระบบตัดเส้นนี้ให้ รายละเอียดและข้อตกลงที่รองรับอยู่ใน §3.1

> คะแนนที่ประกาศไม่ได้มาจากการถอดบัตร แต่มาจาก `Candidate.score` ที่นับไปตั้งแต่ตอนโหวต
> การถอดบัตรใช้เฉพาะตอนมีข้อพิพาทเท่านั้น เพราะฉะนั้น **กุญแจถอดบัตรหาย ไม่ทำให้ผลเลือกตั้งเสีย**

## 2. กุญแจ 3 ดอก

### รันคำสั่งแล้วเกิดอะไรขึ้นบนจอ

อ่านข้อนี้ก่อน เพราะกุญแจทั้งหมดเกิดขึ้นตรงนี้ที่เดียว

```bash
node scripts/generate-election-keys.js --out key-2569.enc
```

**1. จอจะถามว่า** `ตั้งรหัสผ่านใหม่สำหรับไฟล์กุญแจ:`

รหัสผ่านนี้ **คุณคิดขึ้นมาเองเดี๋ยวนั้น** ไม่ได้มาจากไฟล์ไหน ไม่ได้ถูกสร้างโดยระบบ
และ**ไม่เกี่ยวกับรหัสอะไรที่มีอยู่แล้วทั้งสิ้น** ไม่ใช่รหัส PSU Passport ไม่ใช่รหัสกลางของแอดมิน
ไม่ใช่รหัสฐานข้อมูล เป็นรหัสใหม่เอี่ยมที่มีไว้ล็อกไฟล์ใบเดียวนี้เท่านั้น

**รหัสจะแสดงบนจอขณะพิมพ์** ตั้งใจให้เห็น เพราะรหัสที่พิมพ์เพี้ยนไปตัวเดียวแปลว่าไฟล์นั้นเปิดไม่ได้
อีกตลอดกาล ซึ่งแย่กว่าความเสี่ยงเรื่องคนมองข้ามไหล่มาก **ทำตอนไม่มีใครอยู่ข้างหลัง** และปิดเทอร์มินัล
เมื่อเสร็จ ต้องยาวอย่างน้อย 8 ตัว

**2. ถามซ้ำอีกครั้งให้ยืนยัน** พิมพ์ไม่ตรงกันคือยกเลิก ไม่มีไฟล์ไหนถูกเขียน เริ่มใหม่ได้เลย

**3. ได้ของออกมา 2 ที่**

| ได้อะไร | อยู่ที่ไหน | เอาไปทำอะไร |
|---|---|---|
| ไฟล์ `key-2569.enc` | โฟลเดอร์ที่คุณรันคำสั่ง | ก๊อปไปเก็บให้ปลอดภัย แล้วลบต้นทางทิ้ง |
| ข้อความ 2 บรรทัด | พิมพ์บนจอ | ก๊อปไปวางใน `.env` ของเซิร์ฟเวอร์ |

### รหัสผ่านไม่ใช่กุญแจ ลำดับที่เกิดขึ้นจริง

คนเข้าใจสลับกันตรงนี้บ่อยที่สุด **รหัสผ่านที่คุณพิมพ์ไม่ได้สร้างกุญแจ และไม่ได้เกี่ยวกับตัวกุญแจเลย**

| ลำดับ | เกิดอะไรขึ้น | คุณเกี่ยวตรงไหน |
|---|---|---|
| 1 | สคริปต์สุ่มสร้างกุญแจคู่ RSA กับ chain secret | ไม่เกี่ยว เกิดเองในเสี้ยววินาที |
| 2 | สคริปต์ถามรหัสผ่าน | ตรงนี้ที่คุณพิมพ์ |
| 3 | เอา private key + chain secret ใส่ไฟล์ แล้วล็อกด้วยรหัสผ่านนั้น | |
| 4 | พ่น public key + chain secret ออกจอให้ไปวางใน `.env` | |

**กุญแจเกิดขึ้นก่อนคุณพิมพ์รหัสผ่าน** ถ้าพิมพ์รหัสคนละตัว กุญแจก็ยังเป็นชุดเดิม เปลี่ยนแค่รหัสของตู้ที่เก็บมัน

> private key คือ**ของที่อยู่ในตู้เซฟ** รหัสผ่านคือ**รหัสหมุนของตู้เซฟ** คนละชิ้นกัน

### แล้วไฟล์ `.enc` คืออะไร

**เป็นกล่องที่ล็อกอยู่** ข้างในมีของสองอย่างคือ private key กับสำเนา chain secret
และรหัสผ่านที่คุณเพิ่งตั้งคือกุญแจของกล่องใบนั้น

เก็บเป็นกล่องล็อกแทนที่จะเก็บ private key เปล่า ๆ เพราะถ้าไฟล์หลุดไปอยู่ในมือคนอื่น
เขาจะได้แค่กล่องที่เปิดไม่ออก ไม่ได้ตัวกุญแจจริง

เปิดกล่องดูทีหลังได้ด้วยคำสั่งนี้ แล้วมันจะถาม `ใส่รหัสผ่านของไฟล์กุญแจ:` ซึ่งคือรหัสเดิมที่คุณตั้งไว้
(ตอนเปิดถามครั้งเดียว ไม่ถามซ้ำ)

```bash
node scripts/generate-election-keys.js --decrypt key-2569.enc
```

> **รหัสผ่านนี้ไม่ได้ถูกเก็บไว้ที่ไหนเลยในระบบ** ไม่มีในฐานข้อมูล ไม่มีในไฟล์ ไม่มีปุ่มรีเซ็ต
> ลืมเมื่อไหร่คือเปิดกล่องไม่ได้อีกตลอดกาล
>
> **บันทึกลงตัวจัดการรหัสผ่านของคณะทันทีที่ตั้งเสร็จ** อย่ารอ อย่าจำเอา

### ของ 3 ชิ้นที่ได้มา แต่ละชิ้นทำอะไร

ของ 3 ชิ้นนี้ไม่ได้เป็นพวกเดียวกันทั้งหมด **สองชิ้นแรกเป็นกุญแจคู่** ที่เกิดมาด้วยกันและใช้คู่กัน
ส่วนชิ้นที่สามเป็นคนละเรื่อง มีไว้ตรวจการแก้บัตร ไม่เกี่ยวกับการเข้ารหัส

**กุญแจคู่ทำงานเหมือนตู้ไปรษณีย์** ใครก็หยอดจดหมายเข้าช่องได้ แต่เปิดตู้เอาจดหมายออกมาอ่าน
ได้เฉพาะคนที่ถือกุญแจตู้

| เทียบกับตู้ไปรษณีย์ | ในระบบนี้คือ |
|---|---|
| ช่องหยอดจดหมาย ใครก็ใช้ได้ ไม่ต้องปิดบัง | **public key** อยู่บนเซิร์ฟเวอร์ ใช้ปิดผนึกบัตรทุกใบตอนมีคนโหวต |
| กุญแจเปิดตู้ มีดอกเดียว | **private key** อยู่ในไฟล์ `.enc` นอกเซิร์ฟเวอร์ |

เพราะฉะนั้นเซิร์ฟเวอร์รับบัตรเข้ามาเก็บได้เรื่อย ๆ แต่**เปิดอ่านบัตรที่ตัวเองเก็บไว้ไม่ได้เลย**
นี่คือหัวใจทั้งหมดของระบบ ส่วน **chain secret** เป็นชิ้นที่สาม ทำหน้าที่คนละอย่าง อธิบายใน [§4](#4-โซ่บัตร)

| ดอก | เก็บที่ไหน | ใช้ตอนไหน | หายแล้วเสียอะไร | หลุดแล้วเสียอะไร |
|---|---|---|---|---|
| **PUBLIC KEY** | env `ELECTION_BALLOT_PUBLIC_KEY` บนเซิร์ฟเวอร์ | ทุกครั้งที่มีคนกดโหวต | โหวตไม่ได้ทั้งระบบ (503) | ไม่เสียหาย เป็นของเปิดเผยโดยธรรมชาติ |
| **PRIVATE KEY** | ไฟล์เข้ารหัส `key-<ปี>.enc` เก็บ 2 ที่ **นอกเซิร์ฟเวอร์** | เฉพาะตอนมีข้อพิพาทต้องนับซ้ำ | นับซ้ำไม่ได้ **ผลเลือกตั้งไม่เสีย** | **ร้ายแรงที่สุด** ดู [§3](#3-เหตุผลข้อเดียวที่สำคัญที่สุด) |
| **CHAIN SECRET** | env `BALLOT_CHAIN_SECRET` บนเซิร์ฟเวอร์ **+ สำเนานอกเครื่อง** | ตรวจว่าบัตรถูกแก้หรือไม่ | ตรวจโซ่ไม่ได้อีกเลย บัตรยังอยู่ครบแต่พิสูจน์ไม่ได้ | คนที่เข้าถึงฐานข้อมูลระดับ superuser ได้ จะแก้บัตรแล้วเขียนโซ่ใหม่ให้เนียนได้ |

### สองหน้าจอนี้ให้ของคนละอย่าง อย่าสลับกัน

สคริปต์ตัวเดียวกันพ่นข้อความออกมาสองแบบ ขึ้นกับว่าคุณรันด้วย flag ไหน
**ของที่ลง `.env` มาจากหน้าจอเดียวเท่านั้น**

| รันด้วย | ได้อะไรบนจอ | เอาไปทำอะไร |
|---|---|---|
| `--out` (ตอนสร้าง ปีละครั้ง) | `ELECTION_BALLOT_PUBLIC_KEY` + `BALLOT_CHAIN_SECRET` | **วางลง `.env` ของเซิร์ฟเวอร์ แค่นี้ฝั่งเซิร์ฟเวอร์ก็จบ** |
| `--decrypt` (ตอนมีข้อพิพาท) | **PRIVATE KEY** + สำเนา chain secret | ใช้นับซ้ำแบบ offline **ห้ามแตะเซิร์ฟเวอร์** |

> **PRIVATE KEY ห้ามลง `.env` เด็ดขาด ไม่ว่ากรณีใด**
>
> ถ้าเอาลงไป เซิร์ฟเวอร์จะกลายเป็นเครื่องที่ทั้งเก็บบัตรและถอดบัตรได้เอง ใครยึดเซิร์ฟเวอร์ได้
> ก็รู้หมดว่าใครเลือกใคร ซึ่งเป็นสิ่งเดียวที่ระบบทั้งหมดนี้ออกแบบมาเพื่อกัน
>
> **และจะไม่มีอะไรเตือนคุณเลย** ระบบจะทำงานปกติทุกอย่าง ไม่มี error ไม่มีไฟแดง
> ความลับของผู้ลงคะแนนหายไปเงียบ ๆ โดยไม่มีใครรู้จนกว่าจะสาย

`BALLOT_CHAIN_SECRET` โผล่ทั้งสองหน้าจอ ทำให้สับสนได้ ในหน้า `--decrypt` มันคือ**สำเนาสำรอง**
เผื่อค่าบนเซิร์ฟเวอร์หาย ไม่ใช่ของใหม่ที่ต้องเอาไปใส่ซ้ำ

> **ตอนติดตั้งจริง ไม่มีเหตุผลที่ต้องรัน `--decrypt` เลย** รันแค่ `--out` แล้วก๊อป 2 บรรทัดจากจอนั้นพอ
> เปิดไฟล์กุญแจเมื่อไหร่ก็มีโอกาสให้ private key หลุดเมื่อนั้น เปิดเฉพาะตอนมีข้อพิพาทจริง

### สามอย่างที่ห้ามทำ

- **ห้ามเอา private key ขึ้นเซิร์ฟเวอร์** ไม่ว่ากรณีใด รวมถึงเอาไปวางชั่วคราวแล้วตั้งใจลบทีหลัง
- **ห้ามเก็บ private key ไว้ในชุดสำรองเดียวกับฐานข้อมูล** สำรองชุดเดียวหลุด ได้ครบทั้งคู่
- **ห้ามสร้างกุญแจใหม่ระหว่างหีบเปิดอยู่** บัตรที่ลงไปแล้วจะถอดไม่ออกตลอดกาล และโซ่จะขาด

### เซิร์ฟเวอร์ต้องมีอะไรบ้าง

มีแค่ **public key + chain secret** เท่านั้น ถ้าขาดตัวใดตัวหนึ่ง `/api/vote` จะปฏิเสธการโหวต
ทันที (คืน 503) และ**ไม่เก็บตัวเลือกแบบไม่เข้ารหัสเป็นทางออกสำรอง** ตั้งใจให้พังแบบปิดสนิท
ดีกว่าเก็บบัตรที่อ่านออกไว้โดยไม่มีใครรู้

## 3. เหตุผลข้อเดียวที่สำคัญที่สุด

**ทำไม private key ห้ามอยู่บนเซิร์ฟเวอร์**

ถอดบัตรอย่างเดียวไม่ได้ทำให้รู้ว่าใครเลือกใคร เพราะบัตรไม่มีชื่อคนโหวตอยู่แล้ว ถอดออกมา
ก็ได้แค่ "กองตัวเลือก" ซึ่งก็คือผลที่ประกาศไปแล้ว

อันตรายอยู่ที่**การจับคู่** บัตรเรียงตามลำดับที่ลง (`seq`) ถ้าตารางผู้ใช้เก็บเวลากดใช้สิทธิ์
(`votedAt`) ละเอียดระดับวินาที ใครที่ถือ **ทั้งสำเนาฐานข้อมูลและ private key** พร้อมกันก็เอาสองอย่างนี้
มาเรียงทาบกันแล้วไล่ได้ว่าใบไหนของใคร ระบบจึงเก็บ `votedAt` แค่ระดับชั่วโมง (ดู §3.1)

แปลว่าความลับของการลงคะแนนไม่ได้อยู่ที่การเข้ารหัส แต่อยู่ที่**การแยกกุญแจออกจากที่ที่เก็บข้อมูล**
ตราบใดที่สองอย่างนี้ไม่เคยอยู่ในมือคนเดียวกัน ต่อให้ฐานข้อมูลทั้งก้อนหลุด ก็ยังไล่ไม่ได้ว่าใครเลือกอะไร

### 3.1 เส้นที่เคยจับคู่ผู้ลงคะแนนกับบัตรได้ (ตรวจเมื่อ 2026-10-03)

วัดบนฐานข้อมูลทดสอบ พบสองเส้นที่ไม่ต้องใช้ private key ก็รู้ว่าบัตรใบไหนเป็นของใคร (ใช้กุญแจแล้วจึงรู้ต่อว่าเลือกอะไร)

| เส้น | ก่อนแก้ | ตอนนี้ |
|---|---|---|
| `votedAt` ละเอียดระดับมิลลิวินาที เรียงตามเวลาแล้วตรงกับ `seq` | จับคู่ได้ 4 จาก 4 | เก็บแค่ชั่วโมง คนที่โหวตชั่วโมงเดียวกันได้เวลาเท่ากันหมด จึงไม่เหลือลำดับ |
| แถวผู้ใช้กับแถวบัตรถูกเขียนใน transaction เดียว จึงมี `xmin` ตัวเดียวกัน (`User JOIN Ballot ON u.xmin = b.xmin`) | จับคู่ได้ 4 จาก 4 | **ก่อนรับรองผลยังจับคู่ได้ (วัด 5 จาก 5)** ตอนกดรับรองผล ระบบเขียนแถวผู้ใช้ที่ใช้สิทธิ์แล้วใหม่ทั้งหมด หลังรับรองจับคู่ได้ 0 จาก 10 |

ข้อควรรู้ที่ยังเหลือ:

- **ช่วงเลือกตั้งก่อนกดรับรองผล** เส้น `xmin` ยังอยู่ ใครที่มีสิทธิ์อ่านตารางทั้งสองโดยตรงบนฐานข้อมูลรู้ได้ทันทีว่าบัตรใบไหนเป็นของใคร แต่จะรู้ว่า**เลือกอะไร**ต้องมี private key ด้วย
- **ลำดับแถวในไฟล์ฐานข้อมูล** (`ctid`) ของผู้ใช้เรียงตามลำดับที่โหวตด้วย (วัด 20 คน: ตรงลำดับเดิม 20 จาก 20) ตอนรับรองผลระบบเขียนแถวใหม่ทีละแถวตามลำดับสุ่ม ลำดับหลังรับรองจึงสุ่ม (สหสัมพันธ์ ≈ 0 จาก 1.0 บนตาราง 3,000 แถวตั้งค่าปกติ) แต่ถ้าหน้าของตารางมีที่ว่างเหลือ Postgres เก็บแถวใหม่ไว้หน้าเดิม ลำดับระดับหน้ายังเหลือ (วัด 0.53) จึงให้เจ้าหน้าที่ DB รัน `CLUSTER "User" USING "User_studentId_key"` หลังรับรองผลหนึ่งครั้ง (วัดได้ 0.01–0.03) ดู MAINTENANCE-RUNBOOK §1.1 B
- **แถวเวอร์ชันเก่า** ที่ถูกแทนที่ตอนรับรองผลยังค้างในไฟล์ข้อมูลของ Postgres จนกว่าจะรัน `CLUSTER` ด้านบน (ซึ่งเขียนตารางใหม่ทั้งก้อน) หรือ `VACUUM` จะเก็บ และค้างในไฟล์ WAL ตามรอบของ Postgres
- **ชุดสำรองจาก `scripts/backup.sh` ไม่มีเส้น `xmin`** เพราะ `pg_dump` ไม่ได้ส่งออก `xmin` หรือ `ctid` และแถวที่ restore กลับมาได้เลขใหม่ทั้งหมด (ต่างจากการสำรองแบบคัดลอกไฟล์ฐานข้อมูลทั้งโฟลเดอร์ ซึ่งติดไปด้วย) **แต่ชุดสำรองสองชุดเทียบกันได้** ถ้าระหว่างสองชุดมีผู้โหวตคนเดียว ชื่อที่เพิ่มกับคะแนนที่เพิ่มบอกตัวเลือกของคนนั้นทันทีโดยไม่ต้องใช้กุญแจ ช่วงที่เสี่ยงคือต้นและท้ายของการเปิดหีบ
- **เส้นที่ตรวจพบเพิ่มเมื่อ 2026-11-14** (รายละเอียดและสคริปต์ทำซ้ำใน `docs/SECURITY-AUDIT-2026-11.md` ข้อ F5)
  - แถวคะแนนของพรรค (`Candidate`) ถูกเขียนใน transaction เดียวกับแถวผู้ใช้ `User.xmin = Candidate.xmin` จึงบอก**ตัวเลือก**ของผู้ที่โหวตคนล่าสุดของแต่ละตัวเลือกได้ทันที ไม่ต้องใช้ private key ผู้ที่อ่านฐานข้อมูลซ้ำถี่ ๆ ตลอดวันจะรู้ครบทุกคน
  - WAL ของ PostgreSQL เก็บบันทึกการบวกคะแนนทุกครั้งพร้อมเลข transaction superuser ที่ใช้ `pg_walinspect` กู้ตัวเลือกของผู้ลงคะแนนได้ครบทุกคนก่อนรับรองผล (วัด 250 จาก 250) หลังรับรองผลเส้น `User.xmin` หาย แต่บันทึกใน WAL ยังอยู่จนกว่า PostgreSQL จะหมุนไฟล์ทิ้ง
  - ผู้ที่โหวตเพียงคนเดียวในชั่วโมงนั้น จับคู่กับบัตรได้จาก `votedAt` กับ `hourBucket`
  - สรุป: ก่อนรับรองผล ความลับของผู้ลงคะแนนต่อ**ผู้ที่อ่านฐานข้อมูลโดยตรงได้**ไม่ได้ขึ้นกับ private key อย่างที่ย่อหน้าก่อนหน้าเขียนไว้ ต้องจำกัดจำนวนคนที่เข้าฐานข้อมูลได้ระหว่างเปิดหีบให้น้อยที่สุด

**การตัดสินใจ (เจ้าของระบบ 2026-10-03): ยอมรับช่วงก่อนรับรองผล ไม่แก้เพิ่ม** เหตุผล

- จะรู้ว่าใครเลือกอะไรต้องมีสองอย่างพร้อมกัน คือสิทธิ์อ่านฐานข้อมูลโดยตรง และ private key ที่เก็บนอกเซิร์ฟเวอร์ ปัจจุบันคนที่อ่านฐานข้อมูลโดยตรงได้มีเจ้าหน้าที่คณะคนเดียว
- ช่วงที่เส้นนี้เปิดอยู่คือระหว่างเปิดหีบถึงกดรับรองผลเท่านั้น หลังรับรองจับคู่ไม่ได้แล้ว
- ทางที่ปิดได้หมดคือแยกการเขียนแถวผู้ใช้กับแถวบัตรออกจากกัน ซึ่งขัดกับหลักที่ว่ายึดสิทธิ์ ลงบัตร และนับคะแนน ต้องสำเร็จพร้อมกัน เสี่ยงกับความถูกต้องของคะแนนมากกว่าที่ได้คืน

**กติกาที่ต้องรักษาให้การตัดสินใจนี้ยังถูก:** คนที่เข้าฐานข้อมูลได้โดยตรง กับคนที่ถือ private key (ไฟล์ `.enc` และรหัสผ่าน) **ไม่ควรเป็นคนเดียวกัน** ถ้ายังเป็นคนเดียวกันอย่างที่เขียนไว้ใน "ตอนนี้คณะเก็บกุญแจแบบคนเดียวถือ" ด้านล่าง ช่วงก่อนรับรองผลความลับของผู้ลงคะแนนตั้งอยู่บนความไว้ใจในตัวเจ้าหน้าที่คนนั้นคนเดียว แยกคนถือเมื่อไร ต้องร่วมมือกันสองคนจึงจะรู้ได้

ถ้าวันหนึ่งต้องการปิดช่วงนี้จริง ทางเลือกที่ประเมินไว้ (เรียงจากถูกไปแพง): งานเบื้องหลังที่เขียนแถวผู้ใช้ที่โหวตแล้วใหม่ทุกไม่กี่นาที (ย่นช่วงให้สั้นลง ไม่ปิดสนิท) ส่งบัตรผ่านคิวที่บันทึกเป็นชุดแบบสลับลำดับ แยกการโหวตเป็นสอง transaction พร้อมตัวกระทบยอด

ผู้ดูแลฐานข้อมูลให้ถือว่าเส้นนี้ปิดสนิทเฉพาะหลังรับรองผล และหลังรัน `CLUSTER "User" USING "User_studentId_key"` แล้ว

### ตอนนี้คณะเก็บกุญแจแบบคนเดียวถือ

**ปัจจุบันเจ้าหน้าที่ IT ถือทั้งไฟล์และรหัสผ่านเอง** ไม่ได้แบ่งให้ใครถือคนละส่วน
เขียนไว้ตรงนี้เพื่อให้คนที่มารับช่วงต่อรู้ว่าระบบกันอะไรได้จริงและกันอะไรไม่ได้

| กันได้ | กันไม่ได้ |
|---|---|
| คนนอกที่ยึดเซิร์ฟเวอร์ไปทั้งเครื่อง ไม่มีกุญแจก็ถอดบัตรไม่ได้ | เจ้าหน้าที่ IT เอง เข้าถึงได้ทั้งฐานข้อมูลและกุญแจ จึงจับคู่ได้ในทางเทคนิค |
| คนที่ได้ชุดสำรองฐานข้อมูลไป กุญแจไม่ได้อยู่ในนั้น | คนที่ได้ทั้งไฟล์ `.enc` และรหัสผ่านไปพร้อมกัน |
| การแก้บัตรย้อนหลัง โซ่ยังตรวจจับได้เหมือนเดิม | |

แปลว่าความลับของผู้ลงคะแนน ณ ตอนนี้ตั้งอยู่บน**ความไว้ใจในตัวเจ้าหน้าที่** ไม่ใช่บนโครงสร้าง
ที่บังคับ เป็นข้อตกลงที่หน่วยงานขนาดเล็กเลือกกันได้ตามปกติ แต่ต้องเป็นการเลือกที่รู้ตัว
ไม่ใช่เผลอเป็นไปเอง

**ถ้าวันหนึ่งคณะอยากให้เป็นโครงสร้างจริง** ทำได้ทันทีโดยไม่ต้องแก้โค้ดอะไรเลย ให้ไฟล์ `.enc`
กับคนหนึ่ง บอกรหัสผ่านอีกคนหนึ่ง คนเดียวเปิดไม่ได้ ต้องมาเจอกันถึงจะเปิดได้ ได้ผลเท่าซองปิดผนึก
สองซองแต่ไม่มีกระดาษให้หาย คนที่สองควรเป็นเจ้าหน้าที่ประจำ ไม่ใช่นักศึกษา เพราะกุญแจต้องอยู่
ได้นานกว่าวาระของสโมสรฯ

### สิ่งที่ทำได้ทันทีแม้ถือคนเดียว

- **เก็บรหัสผ่านในตัวจัดการรหัสผ่านของคณะ ไม่ใช่ของส่วนตัว** ถ้าเจ้าหน้าที่ลาออกกะทันหัน คณะยังเปิดได้
- **ทำลายกุญแจให้ตรงเวลาตาม [§6](#6-อายุของกุญแจ)** ยิ่งเก็บสั้น ช่วงที่มีความเสี่ยงยิ่งสั้น
- **กรอกใบบันทึกใน [§7](#7-ใบบันทึกผู้ถือกุญแจ) ทุกปี** ให้เป็นสถานะที่มีคนรู้ ไม่ใช่เรื่องที่ไม่มีใครเคยถาม

## 4. โซ่บัตร

การเข้ารหัสกันคนอ่าน แต่ไม่ได้กันคนแก้ โซ่บัตรคือส่วนที่กันการแก้

บัตรทุกใบเก็บลายนิ้วมือของใบก่อนหน้าไว้ด้วย ใบที่ 2 อ้างถึงใบที่ 1 ใบที่ 3 อ้างถึงใบที่ 2
ต่อกันไปเรื่อย ๆ ทั้งเส้น ถ้ามีคนไปแก้ใบใดใบหนึ่งกลางทาง ลายนิ้วมือของใบนั้นเปลี่ยน ทำให้ใบถัดไป
ที่อ้างถึงมันผิดไปด้วย และผิดต่อกันเป็นทอด ๆ จนสุดเส้น **แก้ใบเดียวก็รู้ทันทีว่ามีการแก้**

**แล้ว chain secret เกี่ยวตรงไหน** ลายนิ้วมือคำนวณมาจากสูตร และ chain secret คือส่วนผสมลับ
ในสูตรนั้น ถ้าไม่รู้ค่านี้ ต่อให้แก้บัตรได้ก็คำนวณลายนิ้วมือใหม่ให้ถูกต้องไม่ได้ โซ่จะขาดให้เห็นอยู่ดี
**นี่คือเหตุผลเดียวที่ chain secret ต้องเป็นความลับ** ไม่ได้เอาไว้เข้ารหัสหรือถอดรหัสอะไรทั้งนั้น

```bash
node scripts/verify-ballot-chain.js     # ตรวจทั้งเส้น + นับจำนวนใบ
node scripts/verify-ballot-chain.js --heads /ที่เก็บนอกเครื่อง/chain-head.log   # + เทียบกับปลายโซ่ที่ export ไว้
```

รันก่อนให้สโมสรฯ ประกาศผลทุกครั้ง ถ้าผ่าน แปลว่าบัตรที่อยู่ในหีบไม่ถูกแก้ แทรก หรือสลับ และยอดรวมตรงกัน

> **สิ่งที่คำสั่งนี้ไม่ได้ตรวจ** (ทดสอบแล้ว 2026-11-14 ดู `docs/SECURITY-AUDIT-2026-11.md` ข้อ F1 ถึง F3)
>
> - **คะแนนรายพรรค** ตรวจแค่ว่าผลรวมคะแนนเท่ากับจำนวนบัตร ถ้ามีคนย้ายคะแนนจากพรรคหนึ่งไปอีกพรรคในตาราง `Candidate` คำสั่งนี้ยังรายงานว่าผ่าน
> - **บัตรที่ถูกลบจากท้ายหีบ** หรือหายไปเพราะกู้ข้อมูลสำรองเก่า ถ้าปลายโซ่ ยอดคะแนน และสถานะผู้ใช้ถูกปรับให้ตรงกัน คำสั่งนี้ยังรายงานว่าผ่าน **เว้นแต่จะใส่ `--heads <ไฟล์ปลายโซ่ที่ export ไว้นอกเครื่อง>`** ซึ่งจะตรวจว่าทุกบรรทัดที่ export ไว้ยังอยู่ในโซ่ปัจจุบัน และบอกจำนวนบัตรที่หายไป
> - **บัตรที่ถูกเพิ่มโดยผู้ที่ควบคุมเซิร์ฟเวอร์ได้** ในนามผู้ที่ไม่มาใช้สิทธิ์
>
> สองข้อแรกจับได้ด้วยการถอดบัตรนับใหม่ (`decrypt-recount.js`) จึง**ควรนับใหม่ก่อนรับรองผลทุกปี ไม่ใช่เฉพาะเมื่อมีข้อพิพาท**

ผลของคำสั่งบอกไว้ที่รหัสออก (exit code) ด้วย: **0** คือผ่านทุกข้อ **2** คือมีค่าไม่ตรง (โซ่ถูกแก้ ยอดไม่เท่ากัน
หรือตัวเลขเปลี่ยนไปจากที่รับรองไว้) **1** คือรันไม่ได้ เช่นไม่ได้ตั้ง chain secret

### ตัวเลขที่ถูกบันทึกไว้ตอนรับรองผล

ตอนเจ้าหน้าที่กดรับรองผล ระบบตรวจโซ่และเทียบจำนวนบัตร คะแนนรวม และจำนวนผู้ลงคะแนนก่อน ถ้าสามค่านี้ไม่ตรงกัน
ระบบจะไม่รับรองให้และบอกเหตุ ถ้าผ่าน ระบบจะบันทึกตัวเลข ณ ตอนนั้นไว้สามอย่าง คือคะแนนของแต่ละตัวเลือก
จำนวนบัตรในหีบ และปลายโซ่ แล้วแสดงไว้ในหน้า ศูนย์ควบคุม ส่วน "ตัวเลขที่รับรองไว้"

**เจ้าหน้าที่ต้องเก็บสำเนาตัวเลขชุดนี้ไว้นอกระบบ** (พิมพ์ลงกระดาษ หรือเก็บไว้อีกเครื่องหนึ่ง) เหตุผลคือคนที่แก้ฐานข้อมูลได้
อาจแก้ตัวเลขให้ตรงกับตัวเองทั้งหมด แต่แก้สำเนาที่อยู่ข้างนอกไม่ได้ หลังรับรองแล้ว คำสั่ง `verify-ballot-chain.js`
จะเทียบฐานข้อมูลปัจจุบันกับตัวเลขชุดนี้ให้ และบอกว่าค่าไหนไม่ตรงกัน เจ้าหน้าที่ควรเทียบกับสำเนาที่เก็บไว้ด้วยตาอีกครั้ง
ผลที่รับรองไปก่อนที่ระบบจะเริ่มบันทึกตัวเลขชุดนี้จะไม่มีค่าให้เทียบ

### ทำไมต้อง export ปลายโซ่ออกไปเก็บข้างนอกด้วย

คนที่มีทั้ง chain secret และสิทธิ์ superuser ในฐานข้อมูล สามารถแก้บัตรแล้วเขียนโซ่ใหม่
ทั้งเส้นให้ต่อกันเนียนได้ โซ่ที่ตรวจตัวเองจึงยังไม่พอ

```bash
node scripts/export-chain-head.js       # ตั้ง cron เก็บปลายโซ่ไว้นอกฐานข้อมูลเป็นระยะ
```

ถ้าปลายโซ่วันนี้ไม่ตรงกับที่ export ไว้เมื่อวาน แปลว่ามีคนเขียนใหม่ การจะแก้บัตรแบบไม่ถูกจับ
จึงต้องได้ทั้ง chain secret **และ** superuser **และ** ต้องย้อนไปแก้ไฟล์ที่ export ออกไปแล้วทุกชุด
ซึ่งอยู่คนละที่กัน

> **บัญชีของเว็บอ่านและเพิ่มบัตรได้ แต่แก้และลบไม่ได้** (`SELECT, INSERT` เท่านั้น) บังคับที่ระดับฐานข้อมูลด้วย
> `scripts/sql/ballot-grants.sql` ต้อง apply บน production เสมอ
>
> ถ้าโปรเซสเว็บถูกยึด ผู้โจมตีจะได้ `BALLOT_CHAIN_SECRET` ไปด้วย (เว็บต้องใช้ค่านี้ต่อโซ่ทุกครั้งที่มีคนโหวต)
> จึงคำนวณ HMAC ของโซ่ได้ แต่แก้หรือลบบัตรที่บันทึกแล้วไม่ได้ ตราบที่ role ฐานข้อมูลของเว็บ (`fms_app`) ถูกล็อกสิทธิ์
> ข้อนี้จึงขึ้นกับการแยก role ล้วน ๆ และต้องไม่ให้โปรเซสเว็บได้รหัสของ role เจ้าของตารางหรือ superuser
> บน Docker ไฟล์ compose ส่ง `.env` ทั้งไฟล์ให้ service web จึงเขียนทับ `MIGRATE_DATABASE_URL`
> `POSTGRES_PASSWORD` และ `BACKUP_DATABASE_URL` เป็นค่าว่างในคอนเทนเนอร์ web ไว้แล้ว (ตรวจตาม STAFF-IT-GUIDE §3.5)
> บนเครื่องที่ไม่ใช้ Docker อย่าใส่สามค่านี้ใน `.env` ที่เว็บอ่าน

## 6. อายุของกุญแจ

**กฎข้อเดียว: กุญแจมีอายุเท่ากับชุดสำรองที่มันเปิดได้**

เจ้าของระบบตัดสินแล้วว่าข้อมูลรายคนไม่เก็บข้ามรอบการเลือกตั้ง หีบบัตรเข้ารหัสและข้อมูลรายคน
(สถานะการใช้สิทธิ์ของผู้ใช้แต่ละคน) เก็บไว้จนถึงวันเริ่มรอบปีถัดไป แล้วถูกลบพร้อมกันตอนล้างข้อมูลขึ้นปีใหม่
([STAFF-IT-GUIDE §5](STAFF-IT-GUIDE.md#annual-reset)) สำเนาสิ้นปีของฐานข้อมูลต้องถูกทำลายในรอบเดียวกัน
ไม่มีการเก็บไว้ต่อเป็นหนึ่งปี

กุญแจต้องอยู่ครบช่วงนั้นเหมือนกัน เพราะบัตรที่ลบแล้วนับใหม่ไม่ได้อีก ไม่งั้นเก็บบัตรไว้ก็เปล่าประโยชน์

| ของ | เก็บถึงเมื่อไหร่ |
|---|---|
| ไฟล์ `key-<ปี>.enc` | จนถึงวันเริ่มรอบปีถัดไป (วันล้างข้อมูลขึ้นปีใหม่) แล้วทำลาย |
| สำเนา chain secret ของปีนั้น | ทำลายพร้อมกัน |
| ชุดสำรองฐานข้อมูลของปีนั้น รวมสำเนาสิ้นปี | ทำลายพร้อมกัน |

**ทำลายทั้งสามอย่างพร้อมกันเสมอ** อย่าทำลายอย่างเดียวแล้วเหลืออีกอย่าง เหลือกุญแจไว้โดยไม่มีบัตร
คือเก็บความเสี่ยงไว้เปล่า ๆ เหลือบัตรไว้โดยไม่มีกุญแจคือเก็บของที่ใช้อะไรไม่ได้

ถ้าไม่กำหนดข้อนี้ไว้ สิ่งที่จะเกิดขึ้นจริงคือกุญแจของทุกปีกองสะสมกันไปเรื่อย ๆ และภายในสามสี่ปี
ก็จะไม่มีใครรู้ว่ามีกี่ชุด อยู่กับใครบ้าง

### ถ้าต้องนับซ้ำจริง

ทำบนเครื่อง offline เท่านั้น **ต้องมีกรรมการอยู่ด้วยเป็นพยาน** ยิ่งกุญแจอยู่กับคนเดียว
การมีพยานยิ่งสำคัญ เพราะเป็นสิ่งเดียวที่ยืนยันได้ว่าการเปิดบัตรครั้งนี้ทำต่อหน้าคนอื่น

**เครื่องที่ใช้ต้องมีครบก่อนตัดเน็ต** เพราะ `decrypt-recount.js` อ่านบัตรจากฐานข้อมูล ไม่ได้อ่านจากไฟล์

- Node.js 22 กับโฟลเดอร์โปรเจกต์รุ่นเดียวกับที่ใช้เลือกตั้ง ติดตั้งแพ็กเกจแล้ว (`npm ci` และ `npx prisma generate`)
- PostgreSQL กับ `psql` บนเครื่องนี้เอง และฐานข้อมูลเปล่าสำหรับนับซ้ำโดยเฉพาะ
- ชุดสำรองฐานข้อมูลของปีนั้น (`db-*.sql.gz` เป็นไฟล์ `root:root 0600` อ่านต้องใช้ `sudo`)
- ไฟล์ `key-<ปี>.enc` พร้อมรหัสผ่าน และสำเนา chain secret ของปีนั้น (ได้จากจอ `--decrypt` ในขั้น 2)

```bash
# 1. กู้ชุดสำรองลงฐานข้อมูลแยกบนเครื่องนี้ ห้ามชี้ไปฐานจริงของเซิร์ฟเวอร์
#    สคริปต์นี้ล้างฐานเป้าหมายก่อนกู้ จึงต้องเป็นฐานเปล่าที่สร้างไว้ใช้งานนี้เท่านั้น
sudo RESTORE_VIA=direct RESTORE_DATABASE_URL="postgresql://USER:PASS@localhost:5432/fms_recount" \
  sh scripts/restore.sh backups/db-YYYYmmdd-HHMMSS.sql.gz

# 2. เปิดไฟล์กุญแจ (ใช้ไฟล์ + รหัสผ่านที่ตั้งไว้ตอนพิธี)
node scripts/generate-election-keys.js --decrypt key-2569.enc

# 3. คัดลอกส่วน PRIVATE KEY ที่พิมพ์ออกมา บันทึกเป็นไฟล์ .pem นอกโปรเจกต์
#    ไม่วางไว้ใน /tmp ธรรมดา ให้ใช้โฟลเดอร์ที่เจ้าของคนเดียวอ่านได้บนหน่วยความจำ
#    (mktemp -d สร้างโฟลเดอร์สิทธิ์ 700 ให้เอง) แล้ววางข้อความลงไฟล์
KEYDIR=$(mktemp -d /dev/shm/recount.XXXXXX)
cat > "$KEYDIR/recount.pem"        # วาง PRIVATE KEY แล้วกด Ctrl+D
chmod 600 "$KEYDIR/recount.pem"

# 4. นับซ้ำ ชี้ฐานที่กู้ไว้ และใส่ chain secret เพื่อให้ตรวจโซ่ด้วย
DATABASE_URL="postgresql://USER:PASS@localhost:5432/fms_recount" \
BALLOT_CHAIN_SECRET="<สำเนา chain secret จากจอ --decrypt>" \
  node scripts/decrypt-recount.js --key "$KEYDIR/recount.pem"; echo "exit=$?"

# 5. ลบไฟล์ทิ้งทันทีหลังใช้ แล้วล้าง scrollback ปิดเทอร์มินัล
shred -u "$KEYDIR/recount.pem" ; rmdir "$KEYDIR"
```

ฐานข้อมูลที่กู้มาในขั้น 1 มีรายชื่อผู้ใช้สิทธิ์อยู่ด้วย เสร็จงานแล้วให้ลบฐานนั้นทิ้ง
ถ้าไม่ตั้ง `BALLOT_CHAIN_SECRET` สคริปต์จะข้ามการตรวจโซ่และพิมพ์ว่าข้าม ผลนับยังออกแต่ไม่ได้ยืนยันว่าบัตรไม่ถูกแก้

> ใส่ `--key` หรือใส่ path เฉย ๆ ก็ได้ทั้งคู่ สคริปต์รับทั้งสองแบบ (แก้ 2026-08-15 เพราะข้อความ
> ท้ายผลลัพธ์ของ `--decrypt` เคยบอกท่าที่สคริปต์ไม่รับ ซึ่งจะไปเจอตอนมีข้อพิพาทพอดี)

ผลที่ได้คือจำนวนบัตรแยกรายพรรค เอาไปเทียบกับ `Candidate.score` ที่ประกาศไป
ถ้าตรงกันคือจบเรื่อง ถ้าไม่ตรง ให้รัน `reconcile-scores.js` ประกอบ แล้วส่งทั้งสองผลให้กรรมการ

รหัสออกของ `decrypt-recount.js` มีสามค่า **0** คือนับได้ครบและตรงกับ `Candidate.score` ทุกพรรค **1** คือรันไม่ได้
(ไม่ระบุไฟล์กุญแจ อ่านไฟล์ไม่ได้ หรือเชื่อมฐานข้อมูลไม่ได้) **2** คือคะแนนนับกับคะแนนในตารางไม่ตรง
มีบัตรที่ถอดรหัสไม่ได้ (กุญแจผิดชุด หรือบัตรเสียหาย) หรือโซ่บัตรไม่ผ่านการตรวจ (ตั้งแต่ 2026-11-14 โซ่ขาดทำให้ได้รหัสออก 2 ด้วย)
ถ้าไม่ได้ตั้ง `BALLOT_CHAIN_SECRET` สคริปต์ข้ามการตรวจโซ่ จึงยังต้องอ่านบรรทัด `chain integrity` ที่พิมพ์ก่อนตารางว่าขึ้น OK ไม่ใช่ skipped

### กดรับรองผลแล้ว นับซ้ำได้ไหม

**ได้ ไม่กระทบอะไรเลย**

ในบันทึก `AdminAuditLog` การกดรับรองผลมีชื่อ action ว่า `ANONYMIZE_BALLOTS` และธงในระบบชื่อ `ballotsAnonymized`
ทั้งสองเป็นชื่อเก่าที่ทำให้เข้าใจผิด มันไม่ได้ลบหรือแก้บัตร เพราะบัตรไม่มีชื่อผู้ลงคะแนนอยู่แล้วตั้งแต่แรก
สิ่งที่การรับรองผลทำจริงคือ**ปิดการเลือกตั้งอย่างเป็นทางการ** โดยตั้งธง `ballotsAnonymized` ใน `SystemConfig`
บันทึกตัวเลขที่รับรอง และเขียนแถว `User` ของผู้ที่ใช้สิทธิ์แล้วใหม่ทีละแถวตามลำดับสุ่ม เพื่อตัดเส้น `xmin` ที่จับคู่
ผู้ลงคะแนนกับบัตร (ดู §3.1) การเขียนใหม่นี้ไม่เปลี่ยนค่าในแถว **และไม่แตะตาราง `Ballot` แม้แต่แถวเดียว**

**กดได้เฉพาะบัญชีเจ้าหน้าที่คณะ** (`role = STAFF` จาก `admin.js --create-staff`) กรรมการสโมฯ
กดไม่ได้ ระบบปฏิเสธที่ API ไม่ใช่แค่ซ่อนปุ่ม ชื่อกับเวลาของคนที่กดถูกบันทึกไว้และขึ้นบนหน้าผลคะแนน ก่อนรับรองระบบตรวจโซ่และเทียบจำนวนบัตรกับคะแนนและผู้ลงคะแนนให้ ถ้าไม่ตรงกันจะไม่รับรองและบอกเหตุ ถ้าผ่านจะบันทึกตัวเลขที่รับรองไว้ตามหัวข้อ [ตัวเลขที่ถูกบันทึกไว้ตอนรับรองผล](#ตัวเลขที่ถูกบันทึกไว้ตอนรับรองผล)

**กดแล้วระบบล็อก** เปิดหีบใหม่ไม่ได้ เปลี่ยนโหมดไม่ได้ และ `/api/vote` ปฏิเสธทุกคะแนนที่เข้ามาหลังจากนั้น เพราะคะแนนที่มีคนเซ็นรับรองไปแล้วต้องไม่ขยับได้อีก

> **อ่านตาราง `AdminAuditLog` ให้เป็น** ตารางนี้บันทึก*ความพยายาม* ไม่ใช่*ผลลัพธ์* ถ้ากรรมการสโมฯ
> กดปุ่มรับรองผลแล้วโดนปฏิเสธ 403 log ก็ยังขึ้นบรรทัด `ANONYMIZE_BALLOTS` ชื่อเขาอยู่ดี
> **ตัวที่บอกว่าใครรับรองจริงคือ `certifiedBy` ใน `SystemConfig`** ซึ่งเขียนหลังผ่านด่านแล้วเท่านั้น
> (และเป็นตัวที่ขึ้นบนหน้าผลคะแนน) ถ้าสองที่ไม่ตรงกัน ให้เชื่อ `certifiedBy`

| เครื่องมือ | หลังรับรองผลแล้ว |
|---|---|
| `decrypt-recount.js` | ทำงานเหมือนเดิมทุกประการ ไม่ได้อ่านธงนี้ด้วยซ้ำ |
| `verify-ballot-chain.js` | ทำงานเหมือนเดิม และเทียบฐานข้อมูลกับตัวเลขที่รับรองไว้ด้วย |
| `reconcile-scores.js` | ขึ้นข้อความว่าผลถูกรับรองแล้ว แล้วรันเป็นโหมดอ่านอย่างเดียว |

พูดอีกอย่างคือ **ความสามารถในการตรวจสอบย้อนหลังไม่หายไปหลังรับรองผล** ซึ่งเป็นเรื่องที่ควรเป็น
เพราะข้อพิพาทมักเกิด*หลัง*ประกาศผล ไม่ใช่ก่อน
