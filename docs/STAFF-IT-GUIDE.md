## 1. `setup.sh` ทำอะไร และรู้ได้อย่างไรว่าติดตั้งสำเร็จ

หลังเตรียม §3.1–§3.3 แล้ว รันบน **เครื่องเซิร์ฟเวอร์ Linux ในโฟลเดอร์โปรเจกต์**:

```bash
bash scripts/setup.sh
```

`bash` คือโปรแกรมที่อ่านและทำตามคำสั่งในไฟล์ `scripts/setup.sh`
สคริปต์นี้ติดตั้ง/อัปเดตตาราง สร้าง Docker image และเปิดบริการ จึงควรรันในช่วงที่ยังไม่รับคะแนน
ถ้ามีข้อมูลอยู่แล้ว สำรองตาม §6.1 ก่อน แม้สคริปต์ไม่มีคำสั่งล้างคะแนน แต่ migration สามารถเปลี่ยนโครงสร้างข้อมูลได้

### 1.1 ลำดับที่สคริปต์ทำจริง

| ขั้นที่เห็นบนจอ | เบื้องหลังทำอะไร | สิ่งที่ต้องอ่านจากผล |
|---|---|---|
| **1. เครื่องมือ** | หา `node`, `npm`, `docker`, `psql` บนเครื่องโฮสต์ | ไม่มี Node/npm จะหยุด; ไม่มี Docker/psql จะเตือนและข้ามบางงาน ไม่ได้ติดตั้งเครื่องมือให้ |
| **2. ค่าใน `.env`** | ตรวจว่าตัวแปรจำเป็นมีข้อความอยู่ เลือก URL สำหรับ migration และตรวจเงื่อนไข `localhost` บางกรณี | ค่า placeholder หรือรหัสผิดที่ไม่ว่างก็ผ่านด่านนี้ได้ ไม่ได้พิสูจน์ SSO หรือกุญแจว่าถูกต้อง |
| **3. Dependency** | ถ้าไม่มี `node_modules` จะลอง `npm ci`; ถ้าไม่สำเร็จลอง `npm install` | ถ้ามีโฟลเดอร์อยู่แล้วจะข้าม แม้แพ็กเกจเก่า จึงต้องเตรียมเครื่องมือบนโฮสต์ใหม่หลังอัปเดตตาม §6 |
| **4. ฐานข้อมูล** | ถ้า compose มี service `db` จะเปิดก่อน รอ `pg_isready` สูงสุดประมาณ 60 วินาที แล้วใช้ `MIGRATE_DATABASE_URL` รัน `prisma migrate deploy` | ถ้า DB ยังไม่พร้อมจะเตือนแล้วลอง migrate ต่อ; migrate ล้มจะหยุด **ขั้นนี้เกิดก่อน build เว็บ** |
| **4. ล็อกสิทธิ์** | ใช้ `psql` รัน `scripts/sql/ballot-grants.sql` ให้บัญชี `fms_app` เพิ่ม/อ่านบัตรได้ แต่แก้/ลบไม่ได้ | ต้องมี `psql`, ค่า `MIGRATE_DATABASE_URL` ที่ตั้งชัดเจน และ role `fms_app` อยู่แล้ว; ขาดหรือรันไม่สำเร็จจะเตือนแล้วทำต่อ |
| **5. เปิดระบบ** | รัน `docker compose … up -d --build` เพื่อ build image และสร้าง/ปรับปรุงคอนเทนเนอร์ | Build ล้มจะหยุด; `-d` หมายถึงบริการทำงานเบื้องหลังหลังคำสั่งจบ |
| **6. ตรวจเว็บ** | ใช้ `curl` ตรวจหน้าแรกและ `/api/health` ที่ `http://localhost:3000` รอสูงสุดประมาณ 60 วินาที | ต้องเห็นหน้าแรก 200 และ health 200; ถ้าไม่มี `curl` จะเพียงเตือน ถ้าเปลี่ยน port ต้องตรวจ port จริงเองด้วย |
| **6.5. เขียนรูป** | สั่งผู้ใช้ในคอนเทนเนอร์สร้างแล้วลบไฟล์ทดสอบใน root, โฟลเดอร์รูปที่มีอยู่ และเส้นทางจำลองลึกถึง `groupimage/party*` กับ `members/party_*/Modal` | ถ้าเขียนไม่ได้ การอัปโหลดบางช่องหรือทุกช่องจะมีปัญหา ดู §7.2; สคริปต์ตรวจให้แต่ไม่ได้เปลี่ยนเจ้าของโฟลเดอร์ให้ |
| **7. แอดมิน** | ถ้ามี `--admin` จะให้สิทธิ์ผู้ใช้ที่มีอยู่ แล้วแสดงรายชื่อแอดมิน โดยใช้ฐานข้อมูลผ่าน URL ของ migration | ผู้ใช้ต้องมีใน DB ก่อน; **ไม่ได้สร้างผู้ใช้และไม่ได้ออกรหัสกลางให้** ต้องทำ §4.1 ต่อ |

เมื่อจบจะเห็นยอด **ผ่าน · เตือน · ไม่ผ่าน** อ่านทุกบรรทัดเตือนด้วย
มี `ไม่ผ่าน` จะจบด้วยสถานะผิดพลาด แต่คำเตือนอาจยังจบด้วยสถานะ 0 เช่น ล็อกสิทธิ์ไม่สำเร็จ
จึงไม่ควรใช้เพียงคำว่า “จบแล้ว” หรือสถานะ 0 เป็นเกณฑ์ส่งมอบ

### 1.2 ตอน build เกิดอะไรขึ้น

Docker อ่าน [Dockerfile](../Dockerfile) แล้วทำตามลำดับนี้:

1. เตรียม Node.js 22 ใน image และรัน `npm ci` เพื่อติดตั้งแพ็กเกจตาม `package-lock.json`
2. รัน `npx prisma generate` เพื่อสร้างโค้ดเชื่อมฐานข้อมูลจาก `prisma/schema.prisma` ขั้นนี้ไม่ได้สร้างตาราง
3. รัน `npm run build` เพื่อให้ Next.js สร้างโปรแกรมสำหรับใช้งานจริง
4. เตรียม image ที่รัน `node server.js` ด้วยผู้ใช้ `nextjs` หมายเลข UID 1001

Compose ส่งค่า `.env` ให้คอนเทนเนอร์ตอนเปิดบริการ ไฟล์ `.env` ถูกกันออกจากขั้น build โดย `.dockerignore`
รูปใน `public/images` เชื่อมจากโฟลเดอร์บนเซิร์ฟเวอร์เข้าไปในคอนเทนเนอร์ จึงยังอยู่เมื่อเปลี่ยน image และต้องสำรองแยกจาก DB

**Health ผ่านแปลว่าอะไร:** `/api/health` รันเพียง SQL `SELECT 1` เมื่อสำเร็จคืน HTTP 200 และ `{"ok":true,"db":true}`
ยืนยันว่าเว็บต่อ DB ได้ แต่ยังไม่ยืนยันว่าตารางครบ เขียนข้อมูลได้ SSO ถูกต้อง หรือรับคะแนนได้ครบกระบวนการ
ให้ตรวจต่อที่ §3.6 ส่วน Docker ที่ขึ้น `unhealthy` ไม่ได้หมายความว่า `restart: always` จะรีสตาร์ทให้เอง เพราะโปรเซสอาจยังทำงานอยู่

### 1.3 ตัวเลือกของ setup

| คำสั่ง | ใช้เมื่อใด / ผลที่เกิด |
|---|---|
| `bash scripts/setup.sh --check` | ตรวจเครื่องมือ ค่า env สถานะ migration เว็บ และอ่านรายชื่อแอดมิน; ไม่ migrate, ไม่เปิด/build คอนเทนเนอร์, ไม่ตั้งแอดมิน และข้ามการทดสอบเขียนรูป |
| `bash scripts/setup.sh --admin 6610510149` | ทำ setup ปกติแล้วให้สิทธิ์รหัสตัวอย่างนี้ **เปลี่ยนเป็นรหัสจริงและนำเข้าผู้ใช้นั้นก่อน**; ไม่ได้เปลี่ยนรหัสกลาง |
| `bash scripts/setup.sh --compose docker-compose.faculty.yml` | ใช้ compose ไฟล์ที่เตรียมไว้แทนไฟล์หลัก ทุกคำสั่ง Docker ที่ทำเองต่อจากนั้นต้องใช้ `-f docker-compose.faculty.yml` ให้ตรงกัน |

`--check` ไม่ใช่การตรวจแบบไม่มีผลต่อไฟล์เลย: ถ้ายังไม่มี Prisma ในเครื่อง การเรียก `npx` อาจดาวน์โหลดแพ็กเกจ/cache
ควรติดตั้งเครื่องมือโฮสต์ใน §3.1 ก่อน และอ่านผลโดยรู้ว่ามันยังไม่ได้ตรวจการเขียนรูปหรือความพร้อมเลือกตั้งทั้งหมด

งานที่ setup ไม่ทำให้ ได้แก่ สำรองข้อมูล ตั้ง DNS/HTTPS/reverse proxy ลงทะเบียน SSO สร้าง role ฐานข้อมูล
สร้างกุญแจ นำเข้ารายชื่อ สร้างพรรค/ตัวเลือกพิเศษ ตั้งวันเวลา ออกรหัสกลาง และล้างข้อมูลปีเก่า
ตัวสคริปต์และ `--help` บางข้อความยังย่อขั้นตอนหรือใช้คำเก่า ให้ยึดรายละเอียดการทำงานข้างต้น

## 2. วิธีอ่านคำสั่งในคู่มือนี้

คำสั่ง `bash`, `read` และ `export` ด้านล่างใช้ใน **Bash บน Linux** เช่น หลัง SSH เข้าเซิร์ฟเวอร์
ไม่ใช่คำสั่งสำหรับ PowerShell และไม่ใช่ช่อง SQL ในโปรแกรมจัดการฐานข้อมูล
คำสั่ง SQL จะอยู่ในบล็อก `sql` และรันใน `psql` ตามขั้นตอนที่กำกับ

| คำที่ใช้ | ความหมายสำหรับงานนี้ |
|---|---|
| โฮสต์ | เครื่องเซิร์ฟเวอร์ที่คุณ SSH เข้าไปและพิมพ์คำสั่ง |
| คอนเทนเนอร์ / service | โปรแกรมที่ Docker เปิดแยกสภาพแวดล้อม; `web` คือเว็บ และ `db` คือ PostgreSQL ถ้าเลือกใช้ DB ที่แถมมา |
| image / build | ชุดโปรแกรมพร้อมรัน / การสร้างชุดนั้นจากซอร์สโค้ด |
| dependency / `node_modules` | แพ็กเกจที่โปรแกรมต้องใช้ / โฟลเดอร์ที่เก็บแพ็กเกจบนเครื่องนั้น |
| migration | ไฟล์เปลี่ยนโครงสร้างตารางตามลำดับรุ่น; `migrate deploy` ใช้เฉพาะ migration ที่ยังไม่เคยลง |
| Prisma Client / generate | โค้ดที่ Node ใช้คุยกับ DB / การสร้างโค้ดนั้น ไม่ใช่การใส่ข้อมูล |
| role / grant / sequence | บัญชีและสิทธิ์ DB / การให้สิทธิ์ / ตัวออกเลข id ถัดไปของตาราง |
| connection string | URL ที่ระบุบัญชี รหัสผ่าน เครื่อง port และชื่อ DB ถือเป็นข้อมูลลับ |
| HTTP 200 / 503 | เว็บตอบสำเร็จ / บริการไม่พร้อม; ที่ health ของระบบนี้ 503 หมายถึงการตรวจ DB ล้มเหลว |

`ชื่อไฟล์.csv`, `ชื่อผู้ใช้` และค่าที่ขึ้นต้น `REPLACE_` เป็นตัวอย่าง ต้องเปลี่ยนก่อนใช้งาน
`$APP_DATABASE_URL` และ `$MAINT_DATABASE_URL` เป็นตัวแปรชั่วคราวใน Bash ที่คุณตั้งใน §3.2
การมีค่าอยู่ในไฟล์ `.env` **ไม่ได้ทำให้ `$MIGRATE_DATABASE_URL` ใน Bash มีค่าอัตโนมัติ**
ไม่ต้องใช้ `source .env`; ใช้วิธีรับค่าด้านล่างเพื่อลดปัญหาการตีความอักขระในรหัสผ่าน

คำสั่งตรวจ เช่น `--list`, `logs` และ `SELECT` อ่านข้อมูล ส่วน `setup`, `import`, `--grant`, reset และ restore เปลี่ยนข้อมูลหรือบริการ
แต่ละหัวข้อระบุสิ่งที่เปลี่ยนและผลที่ควรเห็น อย่ารันทั้งคู่มือต่อกันเป็นชุดเดียว

## 3. ติดตั้งครั้งแรก

### 3.0 ถ้ามีระบบหรือฐานข้อมูลเดิมอยู่แล้ว

อย่าสร้างฐานข้อมูลหรือ role ทับของเดิม เริ่มจากสำรองใน §6.1 และตรวจรุ่นโค้ด/ประวัติ migration กับทีมพัฒนา
ถ้าฐานข้อมูลเก่าเคยสร้างด้วย `db push` หรือ SQL นอก migration ต้องให้ทีมพัฒนาตรวจวิธีบันทึกฐานเดิมเข้าประวัติ migration ก่อน
อย่ารัน seed, `migrate reset` หรือทำเครื่องหมาย migration ว่าเสร็จแล้วเพื่อข้าม error

โดยเฉพาะรุ่นเก่าที่มี `User.candidateId`: migration เปลี่ยนเป็นบัตรไม่ระบุตัวผู้ใช้จะถอดคอลัมน์นี้
คำเตือนใน migration กำหนดให้ตรึงคะแนนด้วยโปรแกรมรุ่นเก่าก่อนอัปเกรด ให้ทีมพัฒนากับ DBA ตรวจข้อกำหนดนี้และ backup ก่อนใช้ setup

ตรวจว่ามีบัญชี `fms_app` แยกจากเจ้าของ schema, ตัวเว็บใช้บัญชีนี้, กุญแจตรงกับบัตรที่มีอยู่
และมีบัญชี `STAFF` ใช้งานได้ ค่ารุ่นเก่า `ADMIN_PASSWORD_AUTH_EXTRA`, `ADMIN_STUDENT_IDS`,
`ADMIN_PRIVATE_KEY`, `ADMIN_AUTH_SECRET` และ `NEXT_PUBLIC_ADMIN_*` ไม่ใช่วิธีตั้งรหัสแอดมินปัจจุบัน
การเปลี่ยน secret ของ session หรือกุญแจต้องวางแผนผลต่อผู้ใช้/บัตรเดิม ไม่เปลี่ยนเพียงเพราะกำลังอัปเดตโค้ด

### 3.1 เตรียมเครื่องและโค้ด

ต้องมี Linux, Bash, Git, Node.js 22 ตาม Dockerfile, npm, Docker พร้อม Compose plugin,
PostgreSQL client (`psql`), `curl`, `openssl` และพื้นที่สำหรับ image กับ backup
ให้ผู้ดูแลเครื่องติดตั้งเครื่องมือด้วยวิธีมาตรฐานของคณะก่อน คู่มือนี้เริ่มเมื่อได้รับโฟลเดอร์โค้ดรุ่นที่จะใช้งานแล้ว

```bash
pwd
git status --short
git branch --show-current
git rev-parse HEAD
```

รันในโฟลเดอร์โค้ด: `pwd` แสดงตำแหน่งปัจจุบัน, `status --short` แสดงไฟล์ที่แก้/เพิ่ม,
สองคำสั่งท้ายแสดง branch และรหัสรุ่น (commit) จดรหัสรุ่นไว้ในใบส่งมอบ
ต้องเห็น `package.json`, `Dockerfile`, `docker-compose.yml` และ `scripts` ในโฟลเดอร์นี้
ถ้ามีการแก้ไฟล์ค้าง ให้ตรวจว่าเป็น config ประจำเครื่องหรือโค้ดของใครก่อนอัปเดต ไม่ลบทิ้งเพื่อให้ status ว่าง

```bash
node --version
npm --version
docker compose version
docker info
psql --version
curl --version
openssl version
```

แต่ละบรรทัดตรวจว่ามีเครื่องมือนั้น; Node ควรเป็น `v22.x` ส่วน `docker info` ต้องติดต่อ Docker daemon ได้
ถ้าขึ้น `command not found` ให้ติดตั้งเครื่องมือที่ขาด; ถ้า Docker แจ้ง permission/daemon ให้ผู้ดูแลเครื่องแก้สิทธิ์หรือเปิดบริการ
ข้อความ setup ที่แนะนำ Node 20 เป็นข้อความเก่า ให้ยึด Node 22 ตาม Dockerfile นี้

```bash
npm ci
npx prisma generate
```

`npm ci` ติดตั้งแพ็กเกจบนโฮสต์ตาม lockfile และแทนที่ `node_modules` เดิม;
`prisma generate` สร้าง Client ให้คำสั่ง `node scripts/…` ใช้ได้ ทั้งสองคำสั่งยังไม่ migrate/นำเข้าฐานข้อมูล
ต้องจบโดยไม่มี error และมีข้อความว่า Prisma Client ถูกสร้างแล้ว
ถ้า download/lockfile/generate ผิดพลาด ให้แก้จาก error ก่อนต่อ อย่าเปลี่ยนเวอร์ชันแพ็กเกจเองเพื่อข้ามปัญหา
แพ็กเกจชุดนี้แยกจากที่ Docker ติดตั้งระหว่าง build

ถ้าคัดลอกโค้ดมาจาก Windows และ shell แจ้ง `\r: not found` หรือ `illegal option` ตั้งแต่ต้นไฟล์
อาจเป็นการจบบรรทัดแบบ CRLF ให้ตรวจ/แปลงเฉพาะไฟล์ shell ที่มีปัญหาบน Linux ก่อนรันใหม่ เช่น:

```bash
sed -i 's/\r$//' scripts/setup.sh
```

`sed` บรรทัดนี้เอาอักขระ CR ท้ายบรรทัดออกและบันทึกไฟล์เดิม (`-i`) ไม่เปลี่ยนขั้นตอนในสคริปต์
ทำเฉพาะกรณีไฟล์มาจาก Windows แล้วพบปัญหานี้; fresh clone บน Linux ไม่จำเป็นต้องเกิดปัญหาเดียวกัน
ถ้า `restore.sh` ที่รับมามีอาการเดียวกัน ให้ตรวจ line ending ของไฟล์นั้นก่อนเข้ากระบวนการกู้ข้อมูลด้วย

### 3.2 เลือกฐานข้อมูลและตั้ง `.env`

#### เลือกทางเดียว: A ฐานข้อมูลของคณะ หรือ B ฐานข้อมูลใน Docker

| รายการ | A: DB ของคณะ | B: DB ที่มากับ compose |
|---|---|---|
| ใครเปิด PostgreSQL | DBA/ผู้ดูแลฐานข้อมูลของคณะ | Compose service `db` |
| URL ที่เว็บใช้ | `fms_app` ที่ชื่อเครื่อง DB ซึ่งคอนเทนเนอร์เข้าถึงได้ | `fms_app` ที่ `db:5432` |
| URL ของคำสั่งบนโฮสต์ | `fms_app` หรือ `fms_migrate` ที่ชื่อเครื่อง DB | บัญชีตามงาน ที่ `127.0.0.1:5433` หลังเปิด port แบบ loopback |
| วิธีสำรอง | วิธีของ DBA พร้อมสำรองรูปบนเครื่องเว็บ | `scripts/backup.sh` ตาม §6.1 |

**A — ใช้ DB ของคณะ:** ขอ PostgreSQL database และ role สองตัวตาม §3.5 พร้อมเปิดการเชื่อมต่อจากโฮสต์และคอนเทนเนอร์เว็บ
แก้ไฟล์ compose ที่ใช้จริง: เอา service `db` และ `web.depends_on.db` ออก และเอา volume `postgres_data_prod` ออกถ้าไม่ใช้แล้ว
ไฟล์หลักที่มากับโครงการยังมี `db` อยู่ การแก้ `DATABASE_URL` อย่างเดียวไม่ได้ทำให้ Compose เลิกเปิด DB ที่แถมมา
การปรับนี้เป็นการแก้ config ไม่ใช่คำสั่งลบ volume ที่มีข้อมูลอยู่แล้ว
ถ้าเก็บ config แยกเป็น `docker-compose.faculty.yml` ให้ใช้ `--compose` กับ setup และ `docker compose -f …` กับคำสั่งอื่นทุกครั้ง

**B — ใช้ DB ใน Docker:** ไฟล์หลักไม่ได้เปิด port DB ให้โฮสต์ แต่ setup ต้อง migrate จากโฮสต์
เพิ่มสองบรรทัดนี้ใต้ service `db` ใน `docker-compose.yml` โดยรักษาระยะเยื้อง YAML:

```yaml
    ports:
      - "127.0.0.1:5433:5432"
```

แปลว่า port 5433 ของเครื่องโฮสต์ส่งไปยัง PostgreSQL port 5432 ในคอนเทนเนอร์ และรับจากเครื่องนี้เท่านั้น
ถ้า 5433 ถูกใช้อยู่ เลือก port ว่างแล้วเปลี่ยน URL ฝั่งโฮสต์ให้ตรงกัน ค่า `db:5432` ของเว็บยังเหมือนเดิม
อย่าเปิด port DB ทุก network interface เพื่อให้ setup ต่อได้

#### สร้าง `.env` ในโฟลเดอร์โปรเจกต์

ใช้ editor ของเครื่องสร้างไฟล์และแทนค่าทุก `REPLACE_…` ตัวอย่างนี้เป็น **กรณี B**:

```dotenv
DATABASE_URL="postgresql://fms_app:REPLACE_APP_PASSWORD@db:5432/fms_election"
MIGRATE_DATABASE_URL="postgresql://fms_migrate:REPLACE_MIGRATE_PASSWORD@127.0.0.1:5433/fms_election"
POSTGRES_PASSWORD="REPLACE_POSTGRES_PASSWORD"
NEXTAUTH_URL="https://ovs.fms.psu.ac.th"
NEXTAUTH_SECRET="REPLACE_NEXTAUTH_SECRET"
ADMIN_JWT_SECRET="REPLACE_ADMIN_JWT_SECRET"
AUTHENTIK_CLIENT_ID="REPLACE_SSO_CLIENT_ID"
AUTHENTIK_CLIENT_SECRET="REPLACE_SSO_CLIENT_SECRET"
AUTHENTIK_REDIRECT_URI="REPLACE_REGISTERED_SSO_REDIRECT_URI"
ELECTION_BALLOT_PUBLIC_KEY="REPLACE_FROM_KEY_CEREMONY"
BALLOT_CHAIN_SECRET="REPLACE_FROM_KEY_CEREMONY"
BASE_PATH=
NEXT_PUBLIC_BASE_PATH=
ASSET_PREFIX=
NEXT_PUBLIC_ENABLE_MOCK_LOGIN=false
```

| ค่า | เอามาจากไหน / ใช้ทำอะไร |
|---|---|
| `DATABASE_URL` | บัญชี `fms_app` สำหรับเว็บ; กรณี A เปลี่ยน `db` เป็นเครื่อง DB ของคณะและใช้ข้อกำหนด TLS ตาม DBA |
| `MIGRATE_DATABASE_URL` | บัญชีเจ้าของ schema ที่เรียกจากโฮสต์ ใช้ลง migration และ grants; กรณี A เปลี่ยนเครื่อง/port ตาม DBA |
| `POSTGRES_PASSWORD` | รหัสของ `postgres` สำหรับเริ่ม DB ใหม่กรณี B; กรณี A ไม่ใช้ การแก้ env นี้ภายหลังไม่ได้เปลี่ยนรหัสใน DB volume เดิม |
| `NEXTAUTH_URL` | URL HTTPS จริงที่ผู้ใช้เปิดเข้าระบบ |
| `NEXTAUTH_SECRET` / `ADMIN_JWT_SECRET` | secret คนละค่าที่สุ่มสำหรับ session นักศึกษา / cookie แอดมิน |
| `AUTHENTIK_*` | ขอ client id, secret และ redirect URI ที่ลงทะเบียนตรงกันจากผู้ดูแล PSU SSO ไม่เดา URI เอง |
| `ELECTION_BALLOT_PUBLIC_KEY` | public key ใช้เข้ารหัสบัตร ได้จาก §3.3 วางเป็นบรรทัดเดียวตามผลสคริปต์ |
| `BALLOT_CHAIN_SECRET` | secret ตรวจความต่อเนื่องของบัตร ได้จากพิธีเดียวกัน |
| `BASE_PATH`, `NEXT_PUBLIC_BASE_PATH`, `ASSET_PREFIX` | ว่างทั้งสามเมื่อให้บริการที่ root ของโดเมนปัจจุบัน |
| `NEXT_PUBLIC_ENABLE_MOCK_LOGIN` | ตั้ง `false` เพื่อไม่คงค่าทดสอบไว้ใน config; ด่านฝั่งเซิร์ฟเวอร์ที่ปิด mock login จริงคือ `NODE_ENV=production` ซึ่ง compose/Dockerfile กำหนดให้ จึงต้องคง production mode ด้วย |

อย่าเขียนคำอธิบายท้ายบรรทัดค่า env เพราะตัวอ่านของสคริปต์บางตัวอาจนับเป็นส่วนหนึ่งของค่า
รหัสผ่านใน URL ที่มีอักขระพิเศษต้องเข้ารหัสแบบ URL (percent-encoding) โดยให้ DBA ส่ง URL ที่พร้อมใช้
เก็บ `.env` เป็นความลับ ไม่ใส่ Git หรือภาพหน้าจอส่งงาน และไม่คง `.env.local` ของเครื่องพัฒนาไว้บนเซิร์ฟเวอร์
เพราะคำสั่งแต่ละตัวอ่าน env ไม่เหมือนกันและอาจได้รับค่าคนละชุด

```bash
openssl rand -base64 32
openssl rand -hex 32
chmod 600 .env
```

คำสั่งแรกสุ่มค่าใหม่สำหรับ `NEXTAUTH_SECRET`; คำสั่งที่สองสุ่มอีกค่าสำหรับ `ADMIN_JWT_SECRET`
ทั้งสองเพียงแสดงค่าบนจอ คุณต้องนำไปใส่ไฟล์เอง ไม่ใช้ค่าตัวอย่างจากเอกสารอื่น
`chmod 600 .env` ให้เจ้าของไฟล์อ่าน/เขียนได้คนเดียว ให้บัญชีที่รัน Compose เป็นเจ้าของที่เหมาะสม
ถ้ามี permission error ให้ตรวจเจ้าของไฟล์ ไม่เปิดสิทธิ์อ่านให้ทุกคน

#### เตรียม DB และ role ก่อนเรียก setup

**เฉพาะกรณี B ฐานข้อมูลใหม่:** หลังเติม `POSTGRES_PASSWORD` เปิด DB ก่อน:

```bash
docker compose up -d db
docker compose exec -T db pg_isready -U postgres -d fms_election
docker compose exec db psql -U postgres -d fms_election
```

บรรทัดแรกเปิดเฉพาะ DB และสร้างที่เก็บข้อมูลถ้ายังไม่มี; บรรทัดสองตรวจความพร้อม ต้องเห็น `accepting connections`
ถ้ายังไม่พร้อม ดู `docker compose logs --tail 100 db` เพื่ออ่านข้อความ DB เช่น volume หรือรหัสตั้งต้นผิด ก่อนตรวจใหม่
บรรทัดสามเปิดหน้าจอ SQL ด้วยบัญชีผู้ดูแล DB จะเห็น prompt `fms_election=#`
`exec` หมายถึงเรียกคำสั่งในคอนเทนเนอร์ ส่วน `-T` ปิดการจองหน้าจอ เหมาะกับคำสั่งตรวจที่ไม่รับ input

SQL ต่อไปนี้สำหรับ **DB ว่างที่ยังไม่มีสอง role นี้เท่านั้น** กรณี A ให้ DBA เตรียมสิทธิ์เทียบเท่าตามมาตรฐานของคณะ:

```sql
CREATE ROLE fms_migrate LOGIN;
\password fms_migrate
ALTER DATABASE fms_election OWNER TO fms_migrate;
ALTER SCHEMA public OWNER TO fms_migrate;
CREATE ROLE fms_app LOGIN;
\password fms_app
GRANT CONNECT ON DATABASE fms_election TO fms_app;
GRANT USAGE ON SCHEMA public TO fms_app;
\q
```

`CREATE ROLE … LOGIN` สร้างบัญชีที่เข้า DB ได้; `\password` ให้ตั้งรหัสตรงกับ URL ที่เตรียมไว้
`ALTER … OWNER` ให้ `fms_migrate` เป็นเจ้าของ DB/schema สำหรับ migration
`GRANT CONNECT` อนุญาต `fms_app` เข้า DB และ `GRANT USAGE` อนุญาตเข้าถึง schema `public` แต่ยังไม่ได้ให้สิทธิ์ตาราง
`\q` ออกจาก psql กลับ Bash ต้องไม่มี `ERROR` ระหว่างทำ หาก role/ตารางมีอยู่แล้วให้ตรวจของเดิม ไม่รันซ้ำแบบเปลี่ยนเจ้าของโดยไม่ทบทวน

#### ตั้ง URL สำหรับคำสั่งที่รันบนโฮสต์

โฮสต์ไม่รู้จักชื่อ service `db` แบบคอนเทนเนอร์ จึงต้องมี URL ฝั่งโฮสต์ของ **DB เดียวกัน**
กรณี B ใช้ `127.0.0.1:5433`; กรณี A ใช้เครื่อง/port ของ DBA

```bash
read -r -s -p 'วาง URL ของ fms_app ที่โฮสต์ต่อได้: ' APP_DATABASE_URL
printf '\n'
read -r -s -p 'วาง URL ของ fms_migrate ที่โฮสต์ต่อได้: ' MAINT_DATABASE_URL
printf '\n'
```

`read` รับ URL เข้า Bash โดย `-s` ไม่แสดงค่าที่พิมพ์และ `-r` ไม่แปลง backslash; `printf` ขึ้นบรรทัดใหม่หลังรับค่า
ตัวแปรเหล่านี้อยู่เฉพาะ terminal ปัจจุบัน เปิดหน้าต่างใหม่ต้องรับค่าใหม่
เวลาเรียกคำสั่งจะใช้ `DATABASE_URL="$APP_DATABASE_URL" …` เพื่อให้สคริปต์นั้นใช้บัญชีเว็บจากโฮสต์
ไม่ใช้ URL ของ migration แทนเพื่อให้การตรวจสิทธิ์ผ่าน

```bash
psql "$APP_DATABASE_URL" -v ON_ERROR_STOP=1 -c 'SELECT current_database(), current_user;'
psql "$MAINT_DATABASE_URL" -v ON_ERROR_STOP=1 -c 'SELECT current_database(), current_user;'
```

ทั้งสองคำสั่งอ่านชื่อ DB และบัญชีจริง ต้องเป็น DB เดียวกันและเห็น `fms_app` / `fms_migrate` ตามลำดับ
`-c` ให้ psql รัน SQL แล้วออก; `-v ON_ERROR_STOP=1` ให้หยุดเมื่อ SQL ผิด
ถ้าต่อไม่ได้ ให้แก้ host/port/รหัส/สิทธิ์เครือข่ายก่อนต่อ ชื่อ DB ตรงกันอย่างเดียวยังไม่พอถ้า URL ชี้คนละเครื่อง

### 3.3 พิธีสร้างกุญแจบัตร (ก่อนเริ่มการเลือกตั้ง)

เตรียม Node.js และสำเนาไฟล์สคริปต์บน **เครื่องที่เชื่อถือได้นอกเซิร์ฟเวอร์เลือกตั้ง** ก่อนเริ่มพิธี
จากนั้นตัดการเชื่อมต่อเครือข่ายเพื่อสร้างและตรวจไฟล์กุญแจแบบ offline ในสถานที่ที่คณะควบคุมได้
เตรียมโฟลเดอร์ปลายทางนอก repository เช่น USB ของผู้ถือกุญแจ เปลี่ยน path และปีให้ตรงกับงานจริง:

```bash
ELECTION_YEAR=2569 node scripts/generate-election-keys.js --out /media/KEYS/key-2569.enc
```

`ELECTION_YEAR=2569` ใส่ปีกำกับเฉพาะคำสั่งนี้; สคริปต์สร้างคู่กุญแจ RSA และ chain secret ใหม่
แล้วถามรหัสเปิดไฟล์สองครั้ง รหัสที่พิมพ์จะแสดงบนจอ ควรทำในสถานที่ที่ควบคุมการมองเห็น/บันทึกหน้าจอได้
`--out` บันทึก private key, public key และ chain secret ลงไฟล์เข้ารหัส AES-256-GCM
หากมีไฟล์ชื่อนี้แล้วจะปฏิเสธเพื่อไม่เขียนทับ **ถ้าไม่ใส่ `--out` จะพิมพ์ private key แบบอ่านได้ออกจอ**

ผลที่ต้องได้คือไฟล์ `.enc` และ env สองบรรทัดบนจอ นำเฉพาะ `ELECTION_BALLOT_PUBLIC_KEY` กับ `BALLOT_CHAIN_SECRET`
ไปใส่ `.env` ของเซิร์ฟเวอร์ เก็บไฟล์เข้ารหัสสำรองสองที่นอกเซิร์ฟเวอร์และแยกจาก backup DB
บันทึกผู้ถือไฟล์ ผู้ถือรหัส และวิธีขอเปิดตามนโยบายคณะใน [BALLOT-SECURITY-GUIDE.md](BALLOT-SECURITY-GUIDE.md)
หากเลือกให้คนละคนถือไฟล์และรหัส ให้ทดสอบร่วมกันว่ารับมอบครบก่อนลบสำเนาชั่วคราว

เมื่อต้องตรวจว่าเปิดไฟล์สำรองได้ ให้ทำบนเครื่องนอกเซิร์ฟเวอร์ในสถานที่ควบคุม:

```bash
node scripts/generate-election-keys.js --decrypt /media/KEYS/key-2569.enc
```

คำสั่งนี้อ่านไฟล์และถามรหัสเดิม เมื่อสำเร็จแสดง private key กับ chain secret บนจอ ไม่ได้นับคะแนนหรือแก้ DB
ถ้ารหัสผิด/ไฟล์เสียจะเปิดไม่ได้ ต้องแก้การเก็บกุญแจให้เรียบร้อยก่อนเริ่มรับคะแนน
อย่าส่งผลลัพธ์คำสั่งนี้เป็นหลักฐานในแชท; ใบส่งมอบบันทึกเพียงว่าทดสอบเปิดได้และใครถือ
กุญแจใช้ตลอดการเลือกตั้งนั้น **อย่าเปลี่ยนกุญแจหรือ chain secret หลังมีบัตรแล้ว** และอย่าใช้กุญแจเครื่องทดสอบกับเครื่องจริง

### 3.4 รัน setup และเตรียมข้อมูลตั้งต้น

```bash
bash scripts/setup.sh
```

ตอนนี้สคริปต์จะทำขั้นตอนตาม §1 ได้ครบ: DB/role มีแล้ว, URL ถูกตัว, เครื่องมือและ env พร้อม
อ่านทั้ง error และ warning จนจบ ถ้าใช้ compose แยก ต้องเติม `--compose ชื่อไฟล์` ตามที่เลือกใน §3.2
เมื่อ migrate ผ่านแต่ build ล้ม ฐานข้อมูลอาจเปลี่ยนรุ่นไปแล้ว ให้ดู §6.3 ก่อนย้อนโค้ด

**จาก DB ว่าง migration สร้างตาราง แต่ไม่ได้สร้างพรรคหรือรายชื่อนักศึกษาให้**
อย่ารัน `npx prisma db seed` บนเครื่องจริง: seed ที่ผูกใน `package.json` ใช้สร้างผู้ใช้จำลอง 2,000 คน

เตรียมต่อเป็นลำดับ:

1. ทำ §3.5 ตรวจ grants แล้วทำ §4.1 สร้างบัญชีเจ้าหน้าที่และรหัสกลาง
2. เข้าแอดมินตั้งโหมด `PAUSE` ระหว่างเตรียมข้อมูล ปิดการแสดงผลคะแนน และตั้งวันเวลาปีปัจจุบัน
3. ทำ §4.2 นำเข้ารายชื่อ แล้ว §4.1 ให้สิทธิ์กรรมการที่มีข้อมูลแล้ว
4. ให้สโมสรฯ เพิ่มพรรคจริงด้วยปุ่ม “เพิ่มพรรค” และเตรียมตัวเลือกพิเศษตามด้านล่าง
5. ทำ §3.6 ตรวจส่งมอบก่อนเปิดรับคะแนนตามกำหนด

**ตัวเลือกพิเศษที่ต้องตรวจ:** เมื่อเพิ่ม/ลบพรรคผ่านหน้าแอดมิน ระบบจะ sync เบอร์ `0`
(งดออกเสียง) และเบอร์ `-1` (ไม่รับรอง เฉพาะกรณีพรรคเดียว) ให้อัตโนมัติภายใน transaction เดียวกัน
แต่ฐานเดิมที่สร้างก่อนใช้รุ่นนี้ หรือข้อมูลที่นำเข้าตรงโดยไม่ผ่าน API อาจยังขาดได้ ให้ readiness ตรวจทุกครั้ง
หากต้องซ่อมฐานเดิมก่อนมีการลงคะแนน ใช้บัญชี maintenance ตรวจฐานและเปิด psql:

```bash
psql "$MAINT_DATABASE_URL" -v ON_ERROR_STOP=1
```

คำสั่งนี้เปิดหน้าจอ SQL; ใช้บล็อกต่อไปนี้เมื่อยืนยันว่าเป็น DB งานนี้และอยู่ในช่วงเตรียมระบบเท่านั้น:

```sql
BEGIN;
DO $$ BEGIN
  IF EXISTS (SELECT 1 FROM "Ballot") OR EXISTS (SELECT 1 FROM "Candidate" WHERE score <> 0) THEN
    RAISE EXCEPTION 'มีบัตรหรือคะแนนแล้ว หยุดและตรวจสอบก่อน';
  END IF;
END $$;
INSERT INTO "Candidate" (name, number, score)
SELECT 'งดออกเสียง', 0, 0
WHERE NOT EXISTS (SELECT 1 FROM "Candidate" WHERE number = 0);
COMMIT;
SELECT id, name, number, score FROM "Candidate" ORDER BY number;
```

บล็อกนี้ตรวจว่าไม่มีบัตร/คะแนน แล้วเพิ่มเบอร์ 0 เฉพาะเมื่อยังไม่มี จากนั้นแสดงรายการให้ตรวจชื่อและเบอร์
ถ้ามี name ซ้ำในเบอร์อื่นหรือเกิด `ERROR` ให้หยุดหาสาเหตุกับ DBA ไม่ลบแถวเพื่อฝืนให้ผ่าน
**ถ้ามีพรรคจริงเพียงพรรคเดียว** ให้รัน SQL เพิ่มเติมนี้ในหน้าจอ psql เดิมก่อนเริ่มรับคะแนน:

```sql
BEGIN;
DO $$ BEGIN
  IF EXISTS (SELECT 1 FROM "Ballot") OR EXISTS (SELECT 1 FROM "Candidate" WHERE score <> 0) THEN
    RAISE EXCEPTION 'มีบัตรหรือคะแนนแล้ว หยุดและตรวจสอบก่อน';
  END IF;
  IF (SELECT count(*) FROM "Candidate" WHERE number > 0) <> 1 THEN
    RAISE EXCEPTION 'ต้องมีพรรคจริงหนึ่งพรรคก่อนเตรียมตัวเลือกไม่รับรอง';
  END IF;
END $$;
INSERT INTO "Candidate" (name, number, score)
SELECT 'ไม่รับรอง', -1, 0
WHERE NOT EXISTS (SELECT 1 FROM "Candidate" WHERE number = -1);
COMMIT;
SELECT id, name, number, score FROM "Candidate" ORDER BY number;
```

บล็อกนี้ตรวจว่าไม่มีบัตร/คะแนนและมีพรรคจริงหนึ่งพรรค แล้วเพิ่มเบอร์ -1 เฉพาะเมื่อยังไม่มี โดยไม่เปลี่ยนคะแนนเดิม
ผลควรมีพรรคจริง พร้อมเบอร์ 0 และ -1 ครบและคะแนนเป็นศูนย์
พิมพ์ `\q` เพื่อออกจาก psql เมื่อเสร็จ หากมีรายการเดิมอยู่แล้ว ให้ตรวจความถูกต้องของชื่อนั้นแทนการเพิ่มซ้ำ

### 3.5 ทำไมต้องมีบัญชีฐานข้อมูล 2 ตัว และตรวจอย่างไร

ข้อมูลอยู่ใน DB เดียวกัน แต่แยกบัญชีตามงาน:

| บัญชี | หน้าที่ |
|---|---|
| `fms_migrate` | เจ้าของ schema ใช้ลง migration/กำหนดสิทธิ์/งานบำรุงรักษาที่ได้รับอนุมัติ |
| `fms_app` | ตัวเว็บและคำสั่งดูแลข้อมูลทั่วไป ใช้สิทธิ์จำกัด โดยบัตรเป็นอ่านและเพิ่มเท่านั้น |

ข้อจำกัดนี้ป้องกัน **บัญชีเว็บ** แก้/ลบบัตร ไม่ได้ป้องกันเจ้าของตารางหรือ PostgreSQL superuser
หากบัญชี `fms_app` ได้สิทธิ์สูงผ่าน role อื่นหรือถูกตั้งเป็น superuser จะเสียหลักการนี้

หลัง migration และทุกครั้งที่ setup เตือนเรื่อง grants รันบนโฮสต์:

```bash
psql "$MAINT_DATABASE_URL" -v ON_ERROR_STOP=1 -f scripts/sql/ballot-grants.sql
```

`-f` อ่าน SQL จากไฟล์; ไฟล์นี้ให้สิทธิ์ตารางและ sequence สำหรับงานปกติ และถอนสิทธิ์ที่ไม่ต้องการบน `Ballot`, `ChainHead`, `User`
ต้องรันด้วยเจ้าของ schema หลังมีตารางครบแล้ว และจบโดยไม่มี `ERROR`
มันไม่ได้ถอนสิทธิ์เก่าทุกชนิดจากทุกตารางหรือ membership ของ role จึงต้องตรวจสิทธิ์จริงต่อ

```bash
psql "$APP_DATABASE_URL" -v ON_ERROR_STOP=1 -c "SELECT current_user, has_table_privilege(current_user, '\"Ballot\"', 'SELECT') AS can_read, has_table_privilege(current_user, '\"Ballot\"', 'INSERT') AS can_insert, has_table_privilege(current_user, '\"Ballot\"', 'UPDATE') AS can_update, has_table_privilege(current_user, '\"Ballot\"', 'DELETE') AS can_delete, has_table_privilege(current_user, '\"Ballot\"', 'TRUNCATE') AS can_truncate;"
```

นี่เป็นคำสั่งอ่านสิทธิ์ที่บัญชีมีผลจริง ผลต้องเป็น `fms_app` และ `t, t, f, f, f` ตามลำดับ
ถ้าแก้/ลบ/ล้างทั้งตารางได้ ให้ DBA ตรวจ ownership, superuser, role ที่สืบทอด และ grants ก่อนเปิดระบบ
ใช้ preflight ใน §3.6 ตรวจการเพิ่มพรรคและการปฏิเสธลบบัตรอีกชั้น **ห้ามใช้ URL ของ `fms_migrate` รัน preflight**

### 3.6 ตรวจให้พร้อมส่งมอบ

หลังมีผู้ใช้ พรรค ตัวเลือกพิเศษ บัญชีแอดมิน และวันเวลาที่ถูกต้อง รันบนโฮสต์:

```bash
DATABASE_URL="$APP_DATABASE_URL" npm run preflight
```

คำสั่งนี้เรียก `scripts/preflight-year.js` เพื่อตรวจสภาพก่อนเปิดเลือกตั้ง: คะแนน/การใช้สิทธิ์ต้องว่าง
มีผู้มีสิทธิ์ วันเวลาเรียงถูก ผลยังซ่อน บัญชีพร้อม และสิทธิ์ DB เหมาะสม
มันอ่าน config env จาก `.env`/`.env.local` และต่อ DB ตาม `DATABASE_URL` ที่ส่งนำหน้าคำสั่ง

การตรวจสิทธิ์มีการลอง `INSERT Candidate` แล้ว rollback และลอง `DELETE Ballot WHERE false` แล้ว rollback
จึงไม่ทิ้งพรรคหรือเอาบัตรออก แต่เลข sequence ของ Candidate อาจขยับได้ตามปกติของ PostgreSQL
ข้อความ `app can create parties/members` ของสคริปต์หมายถึง **ทดสอบเพิ่ม Candidate เท่านั้น** ยังไม่ได้ลองเขียน Member
และ preflight ไม่ได้ทดสอบความถูกต้องของกุญแจบัตร/SSO

ต้องไม่มี `FAIL`; `WARN` ทุกข้อให้มีคำอธิบายหรือแก้ให้จบ เช่น ไม่มีงดออกเสียง/ผู้มีสิทธิ์ไม่ควรปล่อยผ่านเพียงเพราะจบสถานะ 0
ระหว่างเตรียมงาน `PAUSE` จะขึ้นคำเตือนเรื่องโหมดได้ เมื่อพร้อมให้ตั้ง `AUTO` กับวันเวลาในอนาคตที่ตรวจแล้ว และตรวจอีกครั้งก่อนถึงเวลาเปิด
ถ้ากำลังมีคะแนนจริงอยู่ preflight จะรายงานคะแนนไม่เป็นศูนย์ จึงใช้สำหรับก่อนเปิด ไม่ใช่สั่งล้างคะแนนเพื่อให้รายงานเขียวระหว่างเลือกตั้ง

```bash
curl -i http://localhost:3000/api/health
curl -i https://ovs.fms.psu.ac.th/api/health
```

`curl -i` อ่านทั้งสถานะ HTTP และข้อความตอบกลับ บรรทัดแรกทดสอบเว็บที่เครื่องนี้ บรรทัดสองทดสอบทางโดเมนจริงผ่าน HTTPS
ทั้งคู่ควรได้ 200 และ `{"ok":true,"db":true}` เปลี่ยนโดเมน/port ถ้าสภาพแวดล้อมจริงต่างออกไป
ถ้า local ผ่านแต่โดเมนไม่ผ่าน ให้ตรวจ DNS, certificate, reverse proxy และ firewall; setup ไม่ได้ตั้งสิ่งเหล่านี้ให้

ก่อนลงนามรับมอบ ให้คนใช้งานทดลองที่โดเมนจริง:

- นักศึกษาล็อกอิน PSU SSO กลับถึงระบบได้ และข้อมูลสิทธิ์ตรงกับทะเบียน
- เจ้าหน้าที่กับกรรมการเข้าแอดมินด้วยบัญชีของตนเองได้; เจ้าหน้าที่มีรหัสส่วนตัวสำหรับรับรองผล
- เพิ่ม/แก้พรรคและสมาชิก อัปโหลดรูป แล้วเปิดหน้าสาธารณะดูได้ ตรวจขั้นนี้ก่อนรับคะแนนและลบข้อมูลซ้อมตามขั้นตอนที่ตกลงกัน
- ตรวจวันเวลา โหมด จำนวนผู้มีสิทธิ์ และรูปแบบบัตรร่วมกับสโมสรฯ พร้อมกด “ตรวจความพร้อมระบบ” ในหน้าแอดมิน
- ทดลองลงคะแนนครบกระบวนการในฐานทดสอบที่แยกจากฐานจริง; หากมีคะแนนซ้อมในฐานจริงต้องทำ §5 ให้ครบก่อนเปิดจริง
- มี backup ที่ตรวจแล้วและเคยทดลองกู้ในฐานแยก พร้อมบันทึกผู้ดูแล/ผู้ถือกุญแจ/รุ่นโค้ด/วันตรวจ และรายการเตือนที่ยังเหลือ

## 4. งานประจำที่สโมสรฯ และเจ้าหน้าที่ต้องใช้

ทุกคำสั่งในหัวข้อนี้รันบนโฮสต์ในโฟลเดอร์โปรเจกต์ ต้องมีแพ็กเกจและ Prisma Client ตาม §3.1
และตั้ง `APP_DATABASE_URL` ของ DB งานนี้ตาม §3.2 ไว้ใน terminal นี้แล้ว

### 4.1 บัญชีเจ้าหน้าที่และกรรมการ

```bash
DATABASE_URL="$APP_DATABASE_URL" node scripts/admin.js --create-staff anuwat.s --name "อนุวัฒน์ นามสกุล"
```

เปลี่ยน username/ชื่อจริงเป็นเจ้าหน้าที่รับมอบ คำสั่งสร้างหรืออัปเดตบัญชี `STAFF` พร้อมสิทธิ์แอดมินและรหัสส่วนตัวที่สุ่มให้
ไม่มีชั้นปี จึงไม่ถูกนับเป็นผู้มีสิทธิ์เลือกตั้ง ชื่อจริงจะใช้บันทึกผู้รับรองผล
ผลควรมี username และ password ให้เก็บลงตัวจัดการรหัสผ่านก่อนปิดจอ รหัสกลางของกรรมการเข้า STAFF ไม่ได้
ถ้าลืมรหัสให้รันชื่อผู้ใช้เดิมอีกครั้ง จะเปลี่ยนรหัสและข้อมูลชื่อ/อีเมลตามคำสั่ง ตรวจตัวตนและแจ้งเจ้าของก่อนทำ
เติม `--ask-password` หากต้องการตั้งเอง สคริปต์ถามสองครั้งและแสดงข้อความที่พิมพ์บนจอ ไม่รับรหัสผ่านจาก argument

```bash
DATABASE_URL="$APP_DATABASE_URL" node scripts/admin.js --grant 6610510149
DATABASE_URL="$APP_DATABASE_URL" node scripts/admin.js --rotate-password
DATABASE_URL="$APP_DATABASE_URL" node scripts/admin.js --list
```

รันเฉพาะงานที่ต้องทำ ไม่จำเป็นต้องเปลี่ยนรหัสทุกครั้งที่เพิ่มคน:

| คำสั่ง | ทำอะไร / ควรเห็นอะไร / ถ้าติดขัด |
|---|---|
| `--grant` | ตั้ง `isAdmin=true` ให้รหัสจริงที่แทนตัวอย่าง ไม่สร้างผู้ใช้หรือรหัสผ่าน ถ้าบอกไม่พบ ให้ตรวจการนำเข้าหรือให้นักศึกษาล็อกอิน SSO ก่อน |
| `--rotate-password` | สุ่มรหัสกลางใหม่และเก็บเป็น bcrypt hash ใน DB แสดงรหัสจริงครั้งเดียว รหัสกลางเดิมใช้ล็อกอินไม่ได้แล้ว ต้องแจ้งกรรมการและส่งรหัสใหม่ผ่านช่องทางที่เหมาะสม รหัสส่วนตัวของ STAFF/บัญชีสำรองไม่เปลี่ยน |
| `--list` | อ่านรายชื่อแอดมิน role และสถานะว่าตั้งรหัสกลางแล้วหรือยัง ไม่แสดงรหัสจริงและไม่แก้ข้อมูล ใช้ตรวจว่าชื่อที่ให้สิทธิ์ปรากฏก่อนให้เจ้าตัวลองล็อกอิน |

```bash
DATABASE_URL="$APP_DATABASE_URL" node scripts/admin.js --revoke 6610510149
```

เปลี่ยนเป็นรหัสผู้พ้นหน้าที่ คำสั่งถอด `isAdmin` และล้างรหัสส่วนตัวของบัญชีนั้น มีผลเมื่อเรียก API แอดมินครั้งถัดไป
ไม่ได้ลบผู้ใช้หรือคะแนน รัน `--list` ตรวจชื่อหายจากรายชื่อแอดมิน ถ้าเจ้าตัวรู้รหัสกลางให้เปลี่ยนรหัสกลางด้วย

```bash
DATABASE_URL="$APP_DATABASE_URL" node scripts/admin.js --break-glass --username fms-emergency
```

ใช้เมื่อจำเป็นต้องมีบัญชีสำรองฉุกเฉิน คำสั่งสร้าง/อัปเดต username ที่ระบุเป็น role `ADMIN` และแสดงรหัสส่วนตัวใหม่
เลือกชื่อเฉพาะที่ไม่ชนกับบัญชีนักศึกษา เก็บรหัสกับ IT และใช้ `--revoke fms-emergency` เมื่อเหตุจบ
บัญชีสำรองใหม่นี้ไม่มีชั้นปี แต่ **ไม่ใช่ STAFF สำหรับรับรองผล**

อย่ารัน `--clear-personal` ตามข้อความเตือนโดยไม่ตรวจ: คำสั่งนี้ล้างรหัสส่วนตัว **ทุกบัญชี รวม STAFF**
จึงทำให้เจ้าหน้าที่เสียทางเข้าบัญชีของตน หากเจอรหัสส่วนตัวเก่าของกรรมการ ให้ IT ตรวจบัญชีที่เกี่ยวข้องและวางแผนแก้เฉพาะเป้าหมาย
ข้อความช่วยเหลือของ `admin.js` บางส่วนยังบอกว่า STAFF ใช้รหัสกลาง ให้ยึดการทำงานที่อธิบายไว้ในหัวข้อนี้

### 4.2 นำเข้ารายชื่อผู้มีสิทธิ์

ขอทะเบียนฉบับปีปัจจุบันจากผู้รับผิดชอบ ก่อนนำเข้าตรวจจำนวนกับเจ้าของข้อมูลและสำรองตาม §6.1
เก็บไฟล์ในตำแหน่งที่จำกัดผู้เข้าถึงนอก Git สคริปต์แสดงตัวอย่างห้าคนแรกบนจอ จึงอย่าส่ง log ที่มีข้อมูลส่วนตัวเข้ากลุ่มทั่วไป

ใช้ `.csv` แบบ UTF-8 หรือ `.xlsx` โดยข้อมูลต้องอยู่ **worksheet แรก** และแถวแรกเป็นหัวคอลัมน์
ถ้าได้รับ `.xls` ให้แปลงเป็น `.xlsx` หรือ CSV ก่อน แม้ CLI ระบุว่ารองรับ แต่ตัวอ่านที่ใช้อยู่เป็นตัวอ่าน xlsx

| ชื่อคอลัมน์ที่แนะนำ | หัวภาษาไทยที่รับ | ตัวอย่าง/ความหมาย |
|---|---|---|
| `studentId` | รหัสนักศึกษา | เก็บเป็นข้อความครบทุกหลัก เป็นตัวใช้จับคู่ผู้ใช้ |
| `titleName` | คำนำหน้า | นาย / นางสาว |
| `studNameThai` | ชื่อ | ชื่อจริง |
| `studSnameThai` | นามสกุล | นามสกุล |
| `yearStatus` | ชั้นปี | ใช้เลข `1`, `2`, `3`, `4`; สคริปต์แปลงเป็น `ปี 1`–`ปี 4` ที่ระบบตรวจสิทธิ์ |
| `gender` | เพศ | ชาย / หญิง / อื่นๆ |
| `subKeyid` | รหัสสาขา | รหัสสาขาจากทะเบียน |
| `subMajorId` | — | รหัสสาขาย่อย ถ้ามี |
| `subMajorNameThai` | ชื่อสาขา | ชื่อสาขาจากทะเบียน |

รหัสนักศึกษาต้องไม่หาย ชั้นปีและชื่อควรครบ อย่าใช้ชั้นปีที่เติมเองอย่าง `ปี1` แม้ parser อ่านบางรูปแบบได้
เพราะระบบโหวตเทียบข้อความ `ปี 1`–`ปี 4` แบบตรงตัว การใช้เลข 1–4 ในไฟล์ช่วยให้ได้รูปแบบมาตรฐาน

```bash
DATABASE_URL="$APP_DATABASE_URL" npm run import-students -- /srv/fms-import/students-2569.xlsx
```

เปลี่ยน path เป็นไฟล์ที่ตรวจแล้ว `npm run import-students` เรียกสคริปต์นำเข้า;
`--` ส่ง argument ที่ตามไปให้สคริปต์ คำสั่งนี้ **เขียน DB ทันที ไม่มี dry-run หรือหน้าจอยืนยัน**
คนใหม่จะถูกสร้าง คนเดิมจะอัปเดตข้อมูลที่เปลี่ยนและมีค่าจากทะเบียน โดยไม่เขียนทับด้วย null
ไม่คืนสิทธิ์ `isVoted` ไม่ล้างคะแนน และไม่ลบคนที่หายจากไฟล์ให้อัตโนมัติ

อ่านยอด **สร้างใหม่ · อัปเดต · ข้าม · Error** เทียบกับจำนวนที่คาดไว้ และตรวจตัวอย่างข้อมูลในระบบ
การเขียนเป็นรายแถว ถ้าแถวหนึ่งผิด แถวก่อนหน้าอาจบันทึกแล้ว ต้องแก้รายชื่อ/สาเหตุและตรวจยอดก่อนรันซ้ำ
`Error: 0` อย่างเดียวไม่พอ และไฟล์เดิมที่ข้อมูลตรงทั้งหมดอาจถูกนับ “ข้ามทั้งหมด” พร้อม exit 1 ได้
จึงต้องแยกระหว่างอ่านหัวคอลัมน์ไม่ออกกับไม่มีข้อมูลใหม่จากยอด/ตัวอย่าง ไม่ถือว่ารหัสจบคำสั่งยืนยันความครบถ้วน

หากท้ายรายงานพบคนยังมีสิทธิ์แต่ไม่อยู่ในไฟล์ ให้ตรวจว่าไฟล์เป็น **ทะเบียนทั้งคณะฉบับเต็ม** ก่อนใช้:

```bash
DATABASE_URL="$APP_DATABASE_URL" npm run import-students -- /srv/fms-import/students-2569.xlsx --retire
```

คำสั่งนี้นำเข้าตามปกติ แล้วตั้งชั้นปีเป็น `พ้นสภาพ` สำหรับผู้ใช้ role `student` ปี 1–4 ที่หายจากไฟล์และ `isAdmin=false`
ทำให้คนกลุ่มนั้นลงคะแนนไม่ได้ โดยไม่ลบแถวผู้ใช้ ห้ามใช้กับไฟล์เพิ่มเฉพาะปี 1/บางสาขา
บัญชีนักศึกษาที่เป็นแอดมินถูกยกเว้นจากการ retire ต้องทบทวนผู้พ้นหน้าที่และสิทธิ์ของกลุ่มนี้แยกด้วย

### 4.3 ตรวจคะแนนและรับรองผล

เมื่อปิดรับคะแนนแล้ว ก่อนให้เจ้าหน้าที่รับรองผล รัน:

```bash
DATABASE_URL="$APP_DATABASE_URL" node scripts/reconcile-scores.js
```

อ่าน DB โดยใช้ `BALLOT_CHAIN_SECRET` จาก env ตรวจสายโซ่บัตรและยอดรวมสามทาง:
จำนวนบัตร = ผลรวม `Candidate.score` = จำนวนผู้ใช้ปี 1–4 ที่ `isVoted=true`
ผลต้องเป็น PASS ทุกข้อและยอดทั้งสามเท่ากัน คำสั่งนี้ไม่แก้คะแนน และ **ไม่ได้นับแยกรายพรรคจากบัตรเข้ารหัส**
ถ้า FAIL ให้หยุดการรับรอง ตรวจเหตุร่วมกับทีมพัฒนา/ผู้รับผิดชอบ ไม่มีตัวเลือก `--fix` สำหรับกลบส่วนต่าง

```bash
DATABASE_URL="$APP_DATABASE_URL" node scripts/verify-ballot-chain.js
```

เป็นคำสั่งอ่านเพื่อตรวจสายโซ่และยอดเดียวกันอีกทาง ใช้เมื่อมีข้อสงสัยเกี่ยวกับความต่อเนื่องของบัตร
ผล `CHAIN OK` หมายถึงไม่พบความผิดปกติตามการตรวจนี้; ถ้าต้องนับคะแนนรายพรรคซ้ำต้องทำกระบวนการ offline
กับ private key ตาม [คู่มือความปลอดภัยบัตร](BALLOT-SECURITY-GUIDE.md) ไม่เอา private key ขึ้นเซิร์ฟเวอร์

เมื่อผลตรวจและขั้นตอนของคณะครบ ให้ปิดอย่างเป็นทางการด้วย `ENDED` หรืออยู่ใน `AUTO` ที่พ้นเวลาปิดแล้ว และเปิดเผยผลคะแนนก่อน
จากนั้นเจ้าหน้าที่เข้าด้วยบัญชี `STAFF` ที่ `/admin/login` แล้วรับรองผลในแท็บตั้งค่าระบบ
หากยังอยู่ใน `PAUSE` หรือยังซ่อนผล API จะปฏิเสธการรับรอง
การรับรองบันทึกผู้รับรองและเวลา และปิดทางเปิดหีบใหม่ตามกฎระบบ ให้ตรวจยอด/ชื่อผู้รับรองก่อนกด

## 5. ขึ้นปีใหม่ / ล้างคะแนนซ้อม

ทำเมื่อผู้รับผิดชอบยืนยันให้จบการเลือกตั้งเดิมแล้ว และยังไม่เริ่มรับคะแนนรอบใหม่
ตั้งโหมด `ENDED` ในหน้าแอดมินก่อนเพื่อให้ปิดรับคะแนนแน่นอนตลอดขั้นตอน
ระบบที่รับรองแล้วก็ยอมรับการตั้ง `ENDED` แต่ไม่ยอมเปลี่ยนกลับ `PAUSE`/`AUTO` จนกว่าจะ reset ธงรับรอง
สำรอง DB และรูปตาม §6.1 พร้อมเก็บสำเนาระยะยาวนอกโฟลเดอร์ที่สคริปต์ลบตามอายุ แล้วเก็บ archive ก่อนเปลี่ยนการแสดงผล

### 5.1 เก็บสรุปของปีเดิม

```bash
DATABASE_URL="$APP_DATABASE_URL" npm run archive-year -- --label SAMO-49-final
```

เปลี่ยน label เป็นชื่อปี/รอบที่ต้องการ คำสั่งอ่าน DB แล้วเขียน `results.json`, `design.json`, `README.md`
ลง `archive/SAMO-49-final/` บนโฮสต์ ไม่เปลี่ยน DB แต่ **ชื่อ label ซ้ำจะเขียนทับไฟล์ในโฟลเดอร์เดิม**
เปิดอ่านคะแนน จำนวนผู้มีสิทธิ์ ข้อมูลรับรอง และธีมให้ตรงก่อนเก็บส่งมอบ
archive ไม่ใช่ backup เต็ม: ไม่มีข้อมูลพอคืนฐานข้อมูล/บัตร/รูป จึงต้องมี DB backup และรูปแยกอยู่แล้ว
เมื่อเก็บ archive ครบแล้ว ซ่อนผลในหน้าแอดมินก่อน reset เพื่อไม่ให้ผู้ใช้เห็นคะแนนขณะเตรียมปีใหม่
คง `ENDED` ไว้หลัง reset ระหว่างเตรียมปีใหม่ เพื่อไม่ให้ปลดธงรับรองแล้วเปิดรับคะแนนตามวันที่เก่าโดยไม่ตั้งใจ

### 5.2 ล้างด้วยบัญชี maintenance

หลังมี backup ที่ตรวจแล้วและยืนยัน DB เป้าหมาย รันบนโฮสต์:

```bash
psql "$MAINT_DATABASE_URL" -v ON_ERROR_STOP=1 -c 'SELECT current_database(), current_user;'
psql "$MAINT_DATABASE_URL" -v ON_ERROR_STOP=1 -f scripts/sql/annual-reset.sql
```

บรรทัดแรกอ่านเป้าหมายอีกครั้ง บรรทัดสองทำ SQL ใน transaction และบันทึกผลถ้าทั้งชุดผ่าน
คำสั่งไม่มีหน้าจอถามยืนยัน เมื่อลบแล้วต้องใช้ backup หากต้องการข้อมูลกลับ
ต้องเห็น `BEGIN` ตามด้วยผลคำสั่งและ `COMMIT` โดยไม่มี `ERROR`

| สิ่งที่ reset ทำ | สิ่งที่ยังต้องเตรียมเอง |
|---|---|
| ลบ `Ballot` ทั้งหมด เริ่มเลขบัตรใหม่ และคืน `ChainHead` เป็น `GENESIS`, seq 0 | เก็บ backup/กุญแจของปีเดิมก่อนล้าง |
| ตั้ง `User.isVoted=false`, `votedAt=NULL` **เฉพาะผู้ใช้ปี 1–4** | ไม่ล้าง `isFormCompleted` ไม่ลบผู้ใช้ ไม่เลื่อนชั้นปีหรือ retire ให้ |
| คะแนนทุก Candidate เป็น 0 | รายชื่อพรรค สมาชิก และรูปยังอยู่ ต้องตกลงกับสโมสรฯ ว่าจะใช้ต่อหรือเอาออก |
| ตั้ง `globalConfig.ballotsAnonymized=false` | ไม่ล้าง `certifiedBy`/`certifiedAt`/`certifiedByUsername` ไม่ซ่อน `showResult` ไม่เปลี่ยน `systemMode` หรือวันเวลา |

ถ้าต้องล้างพรรคเก่าด้วย ให้ DBA เตรียม SQL เฉพาะงานพร้อมทบทวนสมาชิก/ตัวเลือกพิเศษ อย่าเปิดคอมเมนต์ท้ายไฟล์แบบอัตโนมัติ
สำหรับข้อมูลผู้รับรองปีเก่าที่ค้าง ให้ DBA ล้างเฉพาะฟิลด์รับรองหลังเก็บ archive แล้ว
เตรียมวันเวลา ซ่อนผล นำเข้าทะเบียนปีใหม่ และตรวจตัวเลือกตาม §3.4 ก่อนคืนโหมด `AUTO` เมื่อพร้อม

```bash
psql "$MAINT_DATABASE_URL" -v ON_ERROR_STOP=1 -c "SELECT (SELECT count(*) FROM \"Ballot\") AS ballots, (SELECT count(*) FROM \"User\" WHERE \"isVoted\" AND year IN ('ปี 1','ปี 2','ปี 3','ปี 4')) AS voted_eligible, (SELECT COALESCE(sum(score),0) FROM \"Candidate\") AS scores;"
DATABASE_URL="$APP_DATABASE_URL" npm run preflight
```

SQL อ่านยอดหลัง reset ต้องได้ `0, 0, 0` ซึ่งนับผู้ใช้เฉพาะช่วงชั้นปีที่ reset แตะ
preflight ตรวจรายการที่เหลือก่อนเปิดรอบใหม่ ต้องอ่านคำเตือนเรื่องโหมด/วันเวลา/ผู้ใช้/พรรคด้วย
ถ้ายอดไม่เป็นศูนย์ ให้ตรวจ SQL error และว่าระบบหยุดรับคะแนนแล้วจริงก่อนทำอะไรต่อ

## 6. สำรองข้อมูลและอัปเดตโค้ด

### 6.1 สำรองก่อนเปลี่ยนระบบ

**กรณี B ใช้ DB ที่มากับ Docker:** รันบนโฮสต์ในโฟลเดอร์โปรเจกต์ เมื่อ DB container ทำงานอยู่:

```bash
sh scripts/backup.sh
```

`sh` รันสคริปต์สำรองที่เขียนสำหรับ POSIX shell ตัวสคริปต์เรียก `pg_dump` ในคอนเทนเนอร์ชื่อ `fms-election-db`
บัญชี `postgres` ฐาน `fms_election` แล้วตรวจว่า dump มีตาราง บีบอัด/ตรวจไฟล์ และเก็บรูป `public/images` ด้วย tar
ผลอยู่ใน `backups/db-วันเวลา.sql.gz` และ `backups/images-วันเวลา.tar.gz`
หลังตรวจผ่านจะลบไฟล์ `db-*.sql.gz` และ `images-*.tar.gz` ในโฟลเดอร์นี้ที่เก่ากว่าเกณฑ์ 14 วัน
**สำเนาสิ้นปีต้องเก็บแยกนอก `backups/`** ไม่เช่นนั้นจะถูกลบตามรอบ

ถ้าขึ้นล้มเหลวให้แก้และสำรองใหม่ก่อนอัปเดต; ถ้าเตือนว่าไม่พบรูปจะได้แค่ DB แม้คำสั่งจบสำเร็จ
การตรวจ gzip/tar ไม่ใช่การทดลองกู้ ให้ซ้อม restore กับ DB แยกก่อนวันเลือกตั้งและบันทึกผล
backup ชุดนี้ไม่เก็บ `.env`, secret, config reverse proxy, role ระดับ cluster หรือไฟล์กุญแจ ต้องมีวิธีเก็บสิ่งเหล่านั้นแยกตามผู้รับผิดชอบ

ถ้าชื่อ DB container จริงต่างจากค่าเริ่มต้น ใช้ตัวเลือกนี้ **หลังตรวจชื่อแล้ว**:

```bash
DB_CONTAINER=fms-election-db sh scripts/backup.sh
```

เปลี่ยนเฉพาะค่าชื่อให้ตรง สคริปต์รับ `POSTGRES_USER`, `POSTGRES_DB`, `IMAGES_DIR`, `OUT_DIR`, `RETENTION_DAYS`
จาก environment ของคำสั่งด้วย แต่ **ไม่ได้อ่าน `DATABASE_URL` เพื่อเลือก DB** อย่าเปลี่ยนชื่อ container แบบเดา

**กรณี A DB ของคณะ:** ให้ DBA สำรองฐานที่เว็บใช้จริงและแจ้งจุดกู้/เวลาสำรอง
อย่าใช้ผล `backup.sh` ยืนยัน DB นี้ เพราะมันจะไป dump คอนเทนเนอร์ชื่อที่ตั้งไว้ ซึ่งอาจเป็นฐานคนละตัว
สำรองรูปจากโฮสต์ด้วยระบบสำรองของคณะหรือคำสั่งนี้ โดยเปลี่ยนชื่อปลายทางให้ไม่ซ้ำและเตรียมโฟลเดอร์ไว้แล้ว:

```bash
tar -czf /srv/fms-backup/images-before-update.tar.gz public/images
tar -tzf /srv/fms-backup/images-before-update.tar.gz
```

บรรทัดแรกอ่านโฟลเดอร์รูปแล้วเขียน archive บีบอัด; ถ้าชื่อไฟล์มีอยู่จะทับ ต้องใช้ชื่อประจำรอบที่ไม่ซ้ำ
บรรทัดสองอ่านรายชื่อใน archive ต้องเห็น `public/images/…` และไม่มี error
เก็บคู่กับจุดสำรอง DB รอบเดียวกันในที่ที่ผู้ดูแลกู้คืนเข้าถึงได้

### 6.2 อัปเดตตามรุ่นที่ตกลง

ทำในช่วงหยุดรับคะแนน (`PAUSE`) ตรวจว่ามี backup ตาม §6.1 แล้ว และจด HEAD เดิมก่อนดึงโค้ด:

```bash
git status --short
git rev-parse HEAD
git pull --ff-only
npm ci
npx prisma generate
bash scripts/setup.sh
```

| คำสั่ง | ผลและวิธีอ่าน |
|---|---|
| `git status --short` | ตรวจการแก้ค้าง รวม compose ที่ปรับประจำเครื่อง อย่าทับ config ของคณะ |
| `git rev-parse HEAD` | แสดงรหัสรุ่นก่อนอัปเดต จดไว้กับชื่อ backup |
| `git pull --ff-only` | ดึง branch ที่ตั้งติดตามไว้ และเลื่อนไปข้างหน้าเฉพาะเมื่อไม่ต้อง merge; ถ้า conflict/diverged ให้ทีมพัฒนาจัดการ ไม่ reset ทิ้ง |
| `npm ci` | ปรับแพ็กเกจโฮสต์ให้ตรง lockfile รุ่นใหม่ จำเป็นเพราะ setup ข้ามเมื่อมี `node_modules` |
| `npx prisma generate` | สร้าง Client รุ่นใหม่สำหรับคำสั่งดูแลบนโฮสต์ |
| `bash scripts/setup.sh` | ลง migration แล้ว grants แล้ว build/เปิดคอนเทนเนอร์และตรวจขั้นต้น; ถ้าใช้ compose แยก เติม `--compose` ให้ตรง |

หลังจบตรวจ local/HTTPS health, แอดมิน, SSO และหน้าสาธารณะที่เกี่ยวข้องตาม §3.6
ใช้ preflight เฉพาะเมื่อเป็นช่วงก่อนเปิดที่คาดว่าคะแนนยังเป็นศูนย์ ถ้ามีคะแนนจริงแล้วให้ตรวจ chain/ยอดตาม §4.3 แทน
คืนโหมดและการแสดงผลตามสถานะเลือกตั้งที่ตกลงกับผู้รับผิดชอบเมื่อการตรวจครบ

### 6.3 ถ้าอัปเดตไม่สำเร็จ

เก็บ error ที่ไม่รวม secret, commit เดิม/ใหม่, เวลาที่รัน และชื่อ backup ให้ทีมพัฒนา
setup ลง migration **ก่อน** build จึงอาจแก้ DB สำเร็จแล้วแม้ build ล้ม
การเอาโค้ดกลับ commit เก่าไม่ได้ทำให้ schema ย้อนกลับ และการรัน setup รุ่นเก่าไม่ใช่คำสั่งยกเลิก migration
ให้ทีมพัฒนาตัดสินว่ารุ่นเก่าเข้ากับ schema ปัจจุบันได้หรือจำเป็นต้องกู้ DB

หากต้อง restore ให้ DBA กำหนด DB เป้าหมาย จุดสำรอง และช่วงหยุดระบบก่อนลงมือ
สำหรับ DB ที่มากับ Docker มี [restore.sh](../scripts/restore.sh) ซึ่งรับไฟล์ DB dump กับ archive รูป
สคริปต์นี้ **ล้างและสร้าง schema `public` ใหม่** ก่อนโหลด dump และเขียนรูปทับ หากโหลดล้มหลังล้าง DB เดิมจะไม่อยู่ในฐานนั้นแล้ว
จึงต้องซ้อมขั้นตอน/ตรวจ target และ backup ในเครื่องแยกก่อน ไม่ใช่คำสั่งลองแก้เว็บล่ม
หลัง restore ตรวจสิทธิ์ `fms_app`, ยอด/chain, รูป และการเข้าระบบตามสภาพที่กู้จริง กรณี DB ของคณะใช้ขั้นตอน restore ของ DBA

## 7. ตรวจเมื่อระบบมีปัญหา

### 7.1 อ่านสถานะก่อนเปลี่ยนระบบ

```bash
docker compose ps
docker compose logs --tail 100 web
docker compose logs --tail 100 db
curl -i http://localhost:3000/api/health
```

`ps` แสดงบริการและสถานะ `running/healthy/unhealthy`; `logs --tail 100` อ่าน 100 บรรทัดล่าสุดของบริการนั้นโดยไม่แก้ข้อมูล
คำสั่ง log ของ `db` ใช้เฉพาะกรณีมี service นี้ ส่วน `curl` ใช้แยกว่าเว็บตอบและต่อ DB ได้หรือไม่
ถ้าใช้ compose ไฟล์แยก ให้เพิ่ม `-f ชื่อไฟล์` หลัง `docker compose` ทุกคำสั่ง
ตรวจและปิดบังรหัสผ่าน/ข้อมูลส่วนบุคคลก่อนส่ง log ให้ผู้ช่วยแก้

| อาการ | จุดที่ควรตรวจ ไม่ใช่ข้อสรุปสาเหตุทันที |
|---|---|
| โดเมนขึ้น 502 แต่ local health ผ่าน | reverse proxy ส่งไป port ถูกหรือไม่, firewall, DNS, HTTPS |
| หน้าแรกขึ้นแต่ health 503 | URL ที่คอนเทนเนอร์ใช้จริง, DNS DB, port, รหัส, TLS, DB พร้อมหรือไม่; `localhost` ในคอนเทนเนอร์หมายถึงตัวมันเอง |
| migrate ต่อ DB ไม่ได้ | `MIGRATE_DATABASE_URL` ต้องต่อจากโฮสต์ได้ โดยเฉพาะ port 5433 ของกรณี B และต้องมีเจ้าของ schema |
| setup บอก node_modules มีแล้ว แต่ admin/preflight พัง | แพ็กเกจหรือ Client บนโฮสต์อาจเก่า ตรวจ `npm ci` และ `npx prisma generate` ตามรุ่นโค้ด |
| เพิ่มพรรคไม่ได้แต่ลบได้ | ดู error ว่าขาด sequence เช่น `Candidate_id_seq` หรือสิทธิ์ตาราง; รัน grants และ preflight ด้วย `fms_app` |
| พรรคที่มีสมาชิกบันทึกไม่ผ่าน | สิทธิ์ `Member`/sequence, รหัสนักศึกษาซ้ำ หรือข้อมูลที่ API ปฏิเสธ; preflight ไม่ได้ทดสอบ Member |
| เปลี่ยนธีม/โหมดไม่ติด | การตอบของ API, session แอดมิน และสิทธิ์ `SystemConfig` ดู log ประกอบ |
| ให้สิทธิ์แล้วคนใช้ยังเข้าไม่ได้ | ตรวจ DB ของคำสั่งตรงกับเว็บ, รายชื่อ `--list`, ใช้รหัสกลาง/รหัส STAFF ถูกประเภท และผู้ใช้มีสิทธิ์จริง |
| โหวตมี error แม้ health ผ่าน | ดู API/log, โหมด/เวลา/สิทธิ์นักศึกษา, กุญแจ และสิทธิ์ตาราง; health ไม่ได้ลองลงคะแนน |

อย่าใช้คำสั่งแสดง `DATABASE_URL` ทั้งค่าเพื่อส่ง screenshot เพราะมีรหัส DB อยู่ในนั้น
ตัวตรวจ localhost ของ setup เป็นเพียงเงื่อนไขเบื้องต้น และอาจถือว่า compose มี override แม้ยังส่งต่อค่าผิดจาก `.env`
จึงต้องยืนยันการเชื่อมต่อจริง ไม่อาศัยข้อความตรวจ URL ผ่านเพียงข้อเดียว

**Build มีข้อความว่าไม่พบ `DATABASE_URL` แต่จบสำเร็จ:** ในการทดสอบ Docker ของคู่มือฉบับนี้
พบข้อความดังกล่าวระหว่างสร้างหน้าล่วงหน้า (static generation) เพราะ `.env` ถูกกันออกจาก image และ build ยังจบสำเร็จได้
อย่าแก้ด้วยการนำรหัส DB ฝังเข้า image ให้ตรวจว่าเป็นข้อความช่วง build หรือ error หลังเปิดบริการ
ถ้า build สำเร็จแล้ว ให้ตรวจ runtime health และการใช้งานตาม §3.6 ต่อ; ถ้า health หลังเปิดบริการยัง 503 ต้องแก้ env/การเชื่อมต่อของคอนเทนเนอร์จริง

```bash
docker compose restart web
```

ใช้เมื่อวิเคราะห์แล้วต้องรีสตาร์ทโปรเซสเว็บ คำสั่งหยุด/เปิดบริการเดิมชั่วคราว ไม่ build image ไม่ migrate และไม่รับ env ที่แก้ใหม่ทั้งหมดแทนการสร้างคอนเทนเนอร์ใหม่
มีช่วงที่ผู้ใช้เข้าไม่ได้ จึงประสานช่วงทำงานและตรวจ health หลังรัน
ถ้าแก้ env ของคอนเทนเนอร์ ต้องใช้ขั้นตอนสร้างบริการใหม่ตาม deployment ที่เลือก ไม่หวังว่า restart อย่างเดียวจะโหลดค่าจากไฟล์ใหม่

### 7.2 อัปโหลดรูปไม่ได้บน Linux

ตรวจก่อนว่า compose ที่ใช้ผูก `./public/images` กับ `/app/public/images` และโปรเซสใช้ UID ใด:

```bash
docker compose exec -T web id
ls -ld public/images
```

คำสั่งแรกอ่านผู้ใช้จริงในคอนเทนเนอร์ รุ่นนี้ควรเห็น UID 1001; คำสั่งสองอ่านเจ้าของ/สิทธิ์โฟลเดอร์บนโฮสต์
ถ้ารูปหลักสมาชิกอัปโหลดได้ แต่โลโก้ รูปหมู่ หรือรูป modal ไม่ได้ อย่าสรุปว่า mount เขียนได้ทั้งหมด:
แต่ละชนิดใช้คนละโฟลเดอร์ย่อย และ ownership อาจไม่เท่ากัน ขั้น 6.5 รุ่นนี้จึงลองเขียนทุกโฟลเดอร์ที่มีอยู่และเส้นทางซ้อนที่ API ใช้จริง
หาก setup ขั้น 6.5 เขียนไม่ได้และยืนยันว่าเป็นปัญหา ownership ของโฟลเดอร์นี้ ให้ผู้ดูแลแก้:

```bash
sudo chown -R 1001 public/images
```

`chown` เปลี่ยนเจ้าของเป็น UID ที่แอปใช้; `-R` ครอบคลุมรูปและโฟลเดอร์ย่อยทั้งหมดใน `public/images`
ตรวจ `pwd` และ target ก่อนรัน เพราะเป็นการเปลี่ยน ownership จริง และอาจมีผลต่อบัญชีที่เคยแก้รูปบนโฮสต์
หากใช้ shared storage/ACL ให้ประสานผู้ดูแล storage แทนการเปลี่ยนแบบเหมารวม ไม่ใช้ `chmod 777`
แล้วลองอัปโหลดจากหน้าแอดมินอีกครั้ง ตรวจว่ารูปปรากฏที่หน้าสาธารณะและไม่ขึ้น permission error ใน log

## 8. ฐานข้อมูลที่ IT ต้องรู้

### 8.1 ตารางหลัก

| ตาราง | เก็บอะไร / เกี่ยวกับงานใด |
|---|---|
| `User` | ผู้ใช้ ข้อมูลทะเบียน ชั้นปี สิทธิ์แอดมิน รหัสที่ hash แล้ว และสถานะมาใช้สิทธิ์; ไม่เก็บพรรคที่คนนี้เลือก |
| `Candidate` / `Member` | พรรค ตัวเลือกพิเศษ คะแนนรวมของแต่ละตัวเลือก / สมาชิกพรรคที่มี foreign key ไป Candidate |
| `Ballot` | บัตรเข้ารหัสพร้อมลำดับและ hash ไม่มี `userId` หรือเวลาละเอียดของผู้ใช้ |
| `ChainHead` | ปลายสายโซ่บัตร แถว id 1 ใช้ควบคุมการเพิ่มบัตรต่อเนื่อง |
| `SystemConfig` | แถว id 1 เก็บโหมด วันเวลา/รายละเอียดใน `globalConfig`, การแสดงผล ธีม และ hash รหัสกลาง |
| `AdminAuditLog` | บันทึกกิจกรรมแอดมินเพื่อสอบย้อนหลัง |
| `Template` | โครงสร้างจากระบบธีมรุ่นก่อน ยังอยู่ใน schema และบางเส้นทางอ่าน จึงไม่ควรลบทิ้งเอง |

ธีมสำเร็จอยู่ในโค้ด ส่วนการเลือกและค่าตั้งที่เกี่ยวข้องอยู่ใน DB การสำรองเฉพาะ DB จึงไม่ใช่การเก็บโค้ดธีมทั้งรุ่น
ไม่มีการเก็บลิงก์ผู้ใช้ไปตัวเลือกโดยตรง แต่ private key ยังต้องแยกจาก DB ตาม §3.3 เพราะ DB มีลำดับบัตรและเวลาการมาใช้สิทธิ์

### 8.2 สิทธิ์ที่ต้องคงไว้

| ตาราง | สิทธิ์ที่บัญชีเว็บใช้ตามไฟล์ grants |
|---|---|
| `Ballot` | `SELECT`, `INSERT` เท่านั้น |
| `ChainHead` | `SELECT`, `UPDATE` |
| `User`, `SystemConfig` | `SELECT`, `INSERT`, `UPDATE` |
| `Candidate`, `Member`, `Template` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| `AdminAuditLog` | `SELECT`, `INSERT` |
| sequences ใน `public` | `USAGE`, `SELECT` สำหรับการออกเลข id |

นี่คือสิทธิ์ที่ไฟล์ [ballot-grants.sql](../scripts/sql/ballot-grants.sql) กำหนด ไม่ใช่หลักฐานว่าสิทธิ์จริงของเครื่องตรงแล้ว
ต้องตรวจบัญชี/สิทธิ์ตาม §3.5 โดยเฉพาะระบบเดิมที่อาจเคยให้สิทธิ์กว้างไว้
`ALTER DEFAULT PRIVILEGES` ใช้กับวัตถุที่จะสร้างโดย role นั้นในอนาคต ไม่แก้สิทธิ์วัตถุเดิมและไม่ได้ทำให้ทุกตารางใหม่เป็น append-only
หลังอัปเดต migration จึงต้องทบทวน grants ด้วยเสมอ
