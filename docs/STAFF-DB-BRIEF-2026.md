# ใบขอ Database ถึง IT คณะ — ระบบเลือกตั้งออนไลน์ สโมสรนักศึกษา (ปีการศึกษา 2569)

> หน้าเดียวจบ สำหรับส่งให้เจ้าหน้าที่ IT ที่ดูแลเซิร์ฟเวอร์ · รายละเอียดเชิงลึกอยู่ที่
> `docs/DEPLOY-CHECKLIST-2026.md` (ฝั่งทีมพัฒนา)

## สิ่งที่ขอ

1. **PostgreSQL 1 database** ชื่อแนะนำ `fms_election` (เวอร์ชันเดิมที่คณะใช้ปีก่อนได้
   — ระบบใช้ Prisma ORM มาตรฐาน ไม่มี extension พิเศษ)
2. **สร้าง role 2 ตัว** (นี่คือจุดที่ต่างจากปีก่อน — ปีนี้แยกสิทธิ์เพื่อความปลอดภัยของบัตรเลือกตั้ง):
   - `fms_migrate` — เจ้าของ schema ใช้ตอนติดตั้ง/อัปเดตโครงสร้างเท่านั้น
   - `fms_app` — role ที่ตัวเว็บใช้จริง สิทธิ์จำกัด (ทีมพัฒนาจะรันสคริปต์
     `scripts/sql/ballot-grants.sql` กำหนดสิทธิ์เองหลัง migrate — ผลคือแอป
     **เพิ่มบัตรได้แต่แก้/ลบบัตรไม่ได้เชิงโครงสร้าง**)
3. ส่ง **connection string ของทั้ง 2 role** ให้ทีมพัฒนา (ผ่านช่องทางปลอดภัย ไม่ส่งแชท/อีเมลเปิด)
4. **Timezone** ของเครื่อง/container ตั้ง `Asia/Bangkok` (ตัวระบบ pin เวลาไทยไว้ใน
   โค้ดแล้ว ข้อนี้กันความสับสนเวลาอ่าน log เท่านั้น)
5. **Backup รายวันตามมาตรฐานคณะ** — ข้อมูลปีนี้อ่อนไหวน้อยกว่าปีก่อนมาก:
   บัตรลงคะแนนถูกเข้ารหัสและ**ไม่ผูกกับตัวผู้โหวต**ตั้งแต่ชั้นโครงสร้าง
   (ใน backup ก็ไม่มีข้อมูลว่าใครเลือกใคร)

## สิ่งที่ *ไม่* ต้องทำ

- ไม่ต้อง restore ข้อมูลปีก่อน — ระบบเริ่ม database ใหม่ทุกปี (รายชื่อผู้มีสิทธิ์
  ทีมพัฒนา import เอง)
- ไม่ต้องเปิด public access — แอปกับ DB คุยกันภายใน (Docker network / localhost)
- ไม่ต้องติดตั้งอะไรใน DB — migration ทีมพัฒนารันเองด้วย role `fms_migrate`

## สรุปความเปลี่ยนแปลงจากปีก่อน (เผื่อถาม)

| เรื่อง | ปีก่อน | ปีนี้ |
|---|---|---|
| role DB | ตัวเดียวสิทธิ์เต็ม | แยก 2: migrate / app (app แก้บัตรไม่ได้) |
| บัตรลงคะแนน | ผูกกับผู้โหวตจนกว่าจะ anonymize | นิรนาม+เข้ารหัสตั้งแต่วินาทีแรก + hash-chain กันแก้ |
| เวลาเปิด-ปิดระบบ | ขึ้นกับ timezone เครื่อง (เคยคลาดเคลื่อน) | pin เวลาไทยในโค้ด ไม่ขึ้นกับ TZ เครื่องแล้ว |
| แอปพลิเคชัน | Docker + subpath `/fms-ovs` | เหมือนเดิม |
