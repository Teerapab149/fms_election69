# รายงานตรวจความปลอดภัยและความถูกต้อง FMS Online Voting System

วันที่ตรวจ 14 พฤศจิกายน 2569 (ค.ศ. 2026) ตรวจที่ commit `43627ef` (branch `main`)
สคริปต์ทดสอบอยู่ใน `scripts/audit/` บน branch `audit/security-review-2026-11` ไม่มีการแก้โค้ดของระบบ

## สรุปสำหรับผู้ตัดสินใจ

ระบบกันสิ่งที่คนทั่วไปกังวลได้จริง: โหวตซ้ำไม่ได้แม้ยิงคำขอพร้อมกัน คนนอกโหวตแทนคนอื่นไม่ได้
คะแนนไม่หลุดออกทาง API ก่อนประกาศ และการแก้บัตรใบใดใบหนึ่งกลางหีบถูกจับได้

จุดอ่อนอยู่ที่อีกด้านหนึ่ง คือ **ผลที่ประกาศพิสูจน์ได้น้อยกว่าที่ README ทำให้เข้าใจ** มีสามเรื่องที่ควรรู้ก่อนนำไปใช้

1. คะแนนที่ประกาศคือตัวเลขในคอลัมน์ `Candidate.score` ซึ่งเครื่องมือตรวจประจำ (ตรวจโซ่ กระทบยอด ปุ่มรับรองผล)
   ตรวจแค่ว่า "ผลรวม" เท่ากับจำนวนบัตร ย้ายคะแนนจากพรรคหนึ่งไปอีกพรรคแล้วเครื่องมือทั้งหมดยังรายงานว่าผ่าน
   มีเพียงการถอดบัตรนับใหม่ด้วย private key เท่านั้นที่จับได้ และคู่มือกำหนดให้ทำเฉพาะเมื่อมีข้อพิพาท
2. ผู้ที่ควบคุมเครื่องเซิร์ฟเวอร์ได้ระหว่างเปิดหีบ สามารถเพิ่มบัตรในนามผู้ที่ไม่มาใช้สิทธิ์ได้ โดยทุกการตรวจผ่าน รวมถึงการนับใหม่
   และผู้ดูแลฐานข้อมูลสามารถตัดบัตรชุดท้ายทิ้งได้โดยไม่ต้องรู้กุญแจโซ่
3. ข้อความ "ไม่มีข้อมูลใดบอกได้ว่าใครเลือกอะไร" ไม่จริงตามตัวอักษร ผู้ที่อ่านฐานข้อมูลได้ในช่วงก่อนรับรองผลระบุตัวเลือกของผู้ลงคะแนนบางคนได้โดยไม่ต้องใช้กุญแจ

ทั้งสามข้อต้องอาศัยสิทธิ์ระดับเซิร์ฟเวอร์หรือฐานข้อมูล ไม่ใช่สิ่งที่นักศึกษาหรือคนนอกทำได้ ส่วนสิ่งที่ **กรรมการสโมสรฯ คนเดียว** ทำได้จากหน้าแอดมิน
คือเปิดดูคะแนนกลางวันเลือกตั้งแล้วเปิดหีบต่อ และแก้ชื่อพรรคหลังมีบัตรแล้วโดยไม่มีบันทึก

## วิธีตรวจและขอบเขต

- อ่านโค้ดทุก API route (30 ไฟล์) ไลบรารีที่เกี่ยวกับบัตร สิทธิ์ และการตรวจผล สคริปต์ของเจ้าหน้าที่ และคู่มือใน `docs/`
- รันโค้ดจริงของระบบกับ PostgreSQL 18.6 ที่ตั้งขึ้นชั่วคราวในเครื่อง (ฐานข้อมูล `fms_audit_e2e` พอร์ต 54329)
  และเปิดแอปด้วย `next dev` ชี้ฐานข้อมูลนั้น ไม่ได้เชื่อมต่อเครื่องจริง ฐานข้อมูลจริง หรือฐานข้อมูล dev ของผู้พัฒนา
- ทุกข้อค้นพบที่ระบุว่า "ยืนยันแล้ว" มีสคริปต์ที่รันซ้ำได้ ดูหัวข้อ [วิธีรันซ้ำ](#วิธีรันซ้ำ)

ความหมายของสถานะ

| สถานะ | ความหมาย |

| ยืนยันแล้ว | รันแล้วเห็นผลตามที่เขียน |

| ถูกต้อง | ตรวจแล้วพบว่าเป็นไปตามที่อ้าง |

<a id="f1"></a>
### F1 ย้ายคะแนนระหว่างพรรคได้ โดยเครื่องมือตรวจประจำทุกตัวยังรายงานว่าผ่าน

**ระดับ** สูง

**ใครทำได้** ผู้ที่เขียนตาราง `Candidate` ได้ ได้แก่ผู้ดูแลฐานข้อมูล และใครก็ตามที่ได้ `DATABASE_URL` ของเว็บหรือยึดโปรเซสเว็บได้
(`scripts/sql/ballot-grants.sql` บรรทัด 74 ให้บัญชีของเว็บ `UPDATE` ตารางนี้ เพราะต้องบวกคะแนนตอนโหวต)
ทำจากหน้าแอดมินไม่ได้ ตรวจแล้วไม่มี API ใดเขียน `score` นอกจาก `/api/vote`

**ผลต่อผลเลือกตั้ง** ผู้ชนะเปลี่ยนได้ และถ้าเจ้าหน้าที่กดรับรองผล ระบบจะบันทึกตัวเลขปลอมเป็น "ตัวเลขที่รับรองไว้"

**สาเหตุ** ผลที่ประกาศคือ `Candidate.score` ส่วน `verifyChain()` ใน `src/lib/chainVerify.js` ตรวจเพียงว่า
จำนวนบัตรเท่ากับผลรวมคะแนนทุกพรรค (บรรทัด 85-91) ไม่ได้ตรวจคะแนนรายพรรค เพราะฝั่งเซิร์ฟเวอร์ถอดบัตรไม่ได้
ฟังก์ชันเดียวกันนี้อยู่เบื้องหลัง `verify-ballot-chain.js`, `reconcile-scores.js`, ข้อตรวจความพร้อม และปุ่มรับรองผล

**ผลที่วัดได้** หีบจริง A 35, B 20, งดออกเสียง 5 หลัง `UPDATE` สองคำสั่ง (A −20, B +20)

```
verify-ballot-chain.js  exit=0   CHAIN OK: no tampering or drift detected.
reconcile-scores.js     exit=0   reconciled, chain intact and score matches the ballot box.
decrypt-recount.js      exit=2   2 candidate(s) drifted.
    1 | AUDIT พรรค A | 15 | 35 | DRIFT
    2 | AUDIT พรรค B | 40 | 20 | DRIFT
```

**ทำซ้ำ** `node scripts/audit/repro-01-verifier-blind-spots.cjs` (กรณี 1 ไม่ต้องใช้ฐานข้อมูล)
และ `node scripts/audit/repro-db-02-real-tools-on-tampered-db.cjs` (กรณี 1 ใช้เครื่องมือจริงกับ PostgreSQL)

**ทางแก้ที่เสนอ** ให้การถอดบัตรนับใหม่ (`decrypt-recount.js`) เป็นขั้นตอนบังคับก่อนรับรองผลทุกปี ไม่ใช่เฉพาะเมื่อมีข้อพิพาท
และแก้ข้อความใน README กับคู่มือที่ทำให้เข้าใจว่าการตรวจโซ่ยืนยันผลรายพรรคได้

### F2 ผู้ที่ควบคุมเซิร์ฟเวอร์ได้ เพิ่มบัตรในนามผู้ที่ไม่มาใช้สิทธิ์ได้ และทุกการตรวจผ่าน

**ระดับ** สูง (เป็นข้อจำกัดของสถาปัตยกรรม)

**ใครทำได้** ผู้ที่อ่าน `.env` ของเซิร์ฟเวอร์ได้หรือยึดโปรเซสเว็บได้ สิ่งที่ต้องใช้มีครบในที่เดียว คือ public key (เข้ารหัสบัตร)
`BALLOT_CHAIN_SECRET` (ต่อโซ่) และบัญชีฐานข้อมูลของเว็บที่ `INSERT` บัตร `UPDATE` ผู้ใช้และคะแนนได้

**ผลต่อผลเลือกตั้ง** เพิ่มคะแนนให้พรรคใดก็ได้เท่าจำนวนผู้ที่ยังไม่ใช้สิทธิ์ การตรวจโซ่ กระทบยอด และการนับใหม่ด้วย private key ตรงกันหมด
ทางเดียวที่จะรู้คือผู้ถูกสวมสิทธิ์มาโหวตแล้วพบว่าระบบแจ้งว่าใช้สิทธิ์ไปแล้ว หรือเทียบจำนวนผู้ใช้สิทธิ์กับหลักฐานภายนอกระบบ

**ผลที่วัดได้** เพิ่มบัตร 15 ใบให้พรรค B ผ่านโค้ด `appendBallotTx` ตัวจริง ผล `verifyChain()` ผ่าน และผลนับใหม่ตรงกับคะแนน (A 35, B 35)

**ทำซ้ำ** `node scripts/audit/repro-01-verifier-blind-spots.cjs` กรณี 3

**ทางแก้ที่เสนอ** ระบุข้อจำกัดนี้ในเอกสารให้ตรง เก็บ log การเข้าสู่ระบบจาก PSU SSO ไว้เทียบจำนวนผู้ใช้สิทธิ์
และพิจารณาแจ้งผู้ลงคะแนนทางอีเมลเมื่อมีการใช้สิทธิ์ เพื่อให้เจ้าตัวเป็นผู้ตรวจ

<a id="f3"></a>
### F3 ลบบัตรชุดท้ายของหีบได้โดยไม่ต้องรู้กุญแจโซ่ และการกู้ข้อมูลสำรองให้ผลเดียวกัน

**ระดับ** สูง

**ใครทำได้** เจ้าของตารางหรือ superuser ของฐานข้อมูล บัญชีของเว็บทำไม่ได้ถ้าลง `ballot-grants.sql` แล้ว
(บนฐานข้อมูลที่ไม่ได้ลง grants เช่นเครื่องพัฒนา บัญชีของเว็บทำได้)

**ผลต่อผลเลือกตั้ง** คะแนนของผู้ที่โหวตช่วงท้ายหายไป เลือกได้ว่าจะหักจากพรรคใด เครื่องมือตรวจรายงานว่าผ่าน

**สาเหตุ** บัตรที่เหลือทุกใบยังต่อกันถูกต้อง และปลายโซ่ใหม่คือค่า `rowHash` ที่อยู่ในตารางอยู่แล้ว จึงไม่ต้องคำนวณ HMAC ใหม่
สิ่งเดียวที่จับได้คือปลายโซ่ที่ `export-chain-head.js` ส่งออกไปเก็บนอกเครื่อง แต่ไม่มีเครื่องมือใดอ่านไฟล์นั้นมาเทียบให้
ต้องเทียบด้วยตา และต้องตั้ง cron เองตามคู่มือ

การกู้ฐานข้อมูลจากชุดสำรอง (สำรองทุก 6 ชั่วโมงตามค่าเริ่มต้น) ระหว่างเปิดหีบให้ผลแบบเดียวกันโดยไม่เจตนา
บัตรหลังจุดสำรองหายทั้งหมด ผู้ที่โหวตไปแล้วกลับเป็น "ยังไม่ใช้สิทธิ์" และไม่มีอะไรแจ้งเตือน

**ผลที่วัดได้** ลบบัตร 10 ใบสุดท้ายจาก 60 ใบ ตั้ง `ChainHead` เป็นบัตรใบที่ 50 หักคะแนนพรรค A 10 คืนสิทธิ์ 10 คน

```
verify-ballot-chain.js  exit=0   CHAIN OK: no tampering or drift detected.
reconcile-scores.js     exit=0   reconciled, chain intact and score matches the ballot box.
decrypt-recount.js      exit=2   3 candidate(s) drifted.
```

การนับใหม่จับได้ในกรณีนี้เพราะผู้ทดสอบไม่รู้ว่าบัตรที่ลบเป็นของพรรคใด ผู้ที่ลบแล้วปรับคะแนนให้ตรงพอดีได้ (เช่นถือ private key ด้วย) จะไม่ถูกจับ

**ทำซ้ำ** `node scripts/audit/repro-db-02-real-tools-on-tampered-db.cjs` กรณี 2

**ทางแก้ที่เสนอ** ให้ `verify-ballot-chain.js` รับไฟล์ปลายโซ่ที่ส่งออกไว้แล้วตรวจว่าทุกบรรทัด (seq, head) ยังอยู่ในโซ่ปัจจุบัน
และเขียนขั้นตอน "กู้ข้อมูลระหว่างเปิดหีบ" ในคู่มือ ว่าต้องประกาศให้ผู้ที่โหวตหลังจุดสำรองมาโหวตใหม่

<a id="f4"></a>
### F4 กรรมการคนเดียวเปิดดูคะแนนกลางวันเลือกตั้งแล้วเปิดหีบต่อได้

**ระดับ** กลาง

**ใครทำได้** บัญชีแอดมินของกรรมการสโมสรฯ คนใดก็ได้ (รหัสกลาง) ไม่ต้องใช้บัญชีเจ้าหน้าที่

**ผลต่อผลเลือกตั้ง** คะแนนรายพรรคถูกเปิดต่อสาธารณะระหว่างที่ยังมีผู้ไม่ได้โหวต แล้วหีบรับคะแนนต่อ ผู้ที่เห็นคะแนนใช้ระดมคนได้
และการเปิดดูสองครั้งคร่อมการโหวตของคนคนหนึ่งบอกได้ว่าคนนั้นเลือกอะไร

**สาเหตุ** `src/lib/election/adminGuards.mjs` ห้ามเปิดหีบเฉพาะขณะที่ผล "กำลังแสดงอยู่" (`checkSetMode` บรรทัด 43)
เมื่อซ่อนผลแล้วด่านนี้ไม่ทำงาน กติกาที่ไฟล์เขียนไว้เองว่า "หีบที่เปิดผลแล้วจะไม่เปิดอีก" จึงไม่ถูกบังคับ
ทำได้สามทาง คือสลับโหมด แก้เวลาปิดหีบ หรือใช้ MANUAL_OPEN

**ผลที่วัดได้** ผ่าน API จริง

```
SET_MODE ENDED → 200     SET_SHOW_RESULT true → 200
anonymous GET /api/results now → isRevealed=true tally 1:9 2:4 0:1
SET_SHOW_RESULT false → 200     SET_MODE MANUAL_OPEN → 200
จากนั้น POST /api/vote ของนักศึกษาอีกคน → 200
```

audit log บันทึกครบทั้งสี่คำสั่ง จึงตรวจย้อนหลังได้ แต่ไม่มีอะไรห้ามหรือแจ้งเตือน

**ทำซ้ำ** `node scripts/audit/repro-02-embargo-peek.mjs` (ไม่ต้องใช้ฐานข้อมูล) และข้อ 4 ของ `repro-http-01-live-app.mjs`

### F5 ระบุตัวเลือกของผู้ลงคะแนนบางคนได้จากฐานข้อมูล โดยไม่ต้องใช้ private key

**ระดับ** กลาง

**ใครทำได้** ผู้ที่อ่านตารางในฐานข้อมูลได้โดยตรง หรือถือชุดสำรองสองชุด ทำจากหน้าเว็บหรือหน้าแอดมินไม่ได้

**ผลต่อผลเลือกตั้ง** ไม่กระทบคะแนน แต่ข้ออ้างเรื่องความลับของการลงคะแนนไม่เป็นจริงสำหรับคนกลุ่มนี้

ทดสอบกับผู้มีสิทธิ์ 2,000 คน โหวต 800 คน โดยเก็บคำตอบจริงไว้ในหน่วยความจำเท่านั้น

| เส้น | ต้องใช้อะไร | ผลก่อนรับรองผล | หลังรับรองผล | สถานะในเอกสารเดิม |
|---|---|---|---|---|
| A `User.xmin = Ballot.xmin` | อ่านสองตาราง | จับคู่ผู้ลงคะแนนกับบัตรได้ 800 จาก 800 (ยังไม่รู้ตัวเลือกถ้าไม่มี private key) | 0 จาก 800 | บันทึกไว้แล้วใน BALLOT-SECURITY-GUIDE §3.1 |
| B `User.xmin = Candidate.xmin` | อ่านสองตาราง | **รู้ตัวเลือกทันที** ของผู้ที่โหวตคนล่าสุดของแต่ละตัวเลือก (3 คน ถูกทั้ง 3) | 0 | **ไม่มีในเอกสาร** |
| D ชั่วโมงที่มีผู้โหวตคนเดียว | อ่านสองตาราง | จับคู่ได้ 2 จาก 2 คนที่โหวตลำพังในชั่วโมงนั้น (`votedAt` กับ `hourBucket`) | ยังอยู่ | ไม่มีในเอกสาร |
| E ภาพสองช่วงเวลา | ชุดสำรองสองชุด หรืออ่านตารางสองครั้ง | ถ้ามีผู้โหวตคนเดียวระหว่างสองภาพ **รู้ตัวเลือกทันที** จากชื่อที่เพิ่มและคะแนนที่เพิ่ม | ยังอยู่ | ไม่มีในเอกสาร |

เส้น B สำคัญที่สุดเพราะไม่ต้องใช้กุญแจและไม่ต้องรอจังหวะ ผู้ที่อ่านฐานข้อมูลซ้ำทุกไม่กี่วินาทีตลอดวันเลือกตั้งจะรู้ตัวเลือกของทุกคน
เส้น E ใช้ได้กับชุดสำรอง `pg_dump` ซึ่งคู่มือเดิมระบุว่าไม่มีเส้นเชื่อม ช่วงที่เสี่ยงคือต้นและท้ายของการเปิดหีบที่มีผู้โหวตน้อย

**ทำซ้ำ** `AUDIT_ROSTER=2000 AUDIT_TURNOUT=800 node scripts/audit/repro-db-01-voter-linkage.cjs`

**ทางแก้ที่เสนอ** แก้ข้อความใน README เป็น "ไม่มีคอลัมน์ใดเชื่อม และหลังรับรองผลจับคู่ไม่ได้" เพิ่มเส้น B, D, E ลงในคู่มือ

### F6 แก้ชื่อและเนื้อหาพรรคได้หลังมีบัตรแล้ว โดยไม่มีบันทึกใด

**ระดับ** กลาง

**ใครทำได้** บัญชีแอดมินของกรรมการคนใดก็ได้

**ผลต่อผลเลือกตั้ง** คะแนนผูกกับแถวของพรรค ไม่ผูกกับชื่อ สลับชื่อสองพรรคแล้วหน้าผลคะแนนจะแสดงชื่อพรรคหนึ่งคู่กับคะแนนของอีกพรรค
และถ้ารับรองผลหลังจากนั้น ชื่อที่ถูกสลับจะถูกบันทึกลง "ตัวเลขที่รับรองไว้" (`certifiedTally` เก็บ เบอร์ ชื่อ คะแนน)

```
now   : เบอร์ 1 "AUDIT พรรค B" score=9   เบอร์ 2 "AUDIT พรรค A" score=5
audit rows written for it: 0
```

**ทางแก้ที่เสนอ** ล็อกชื่อพรรคเมื่อมีบัตรแล้วเช่นเดียวกับหมายเลข และบันทึก audit log ทุกการแก้ข้อมูลพรรค

## ข้อสงสัย ยังพิสูจน์ไม่ได้ในเครื่องนี้

<a id="s1"></a>
**S1 ลำดับแถวทางกายภาพของตารางผู้ใช้บอกลำดับการโหวต** คู่มือเดิมวัดได้ 20 จาก 20 ในการทดสอบนี้วัดได้ไม่ตรงกัน
คือ 6 จาก 40 บนตาราง 60 แถว และสหสัมพันธ์ −0.03 บนตาราง 2,000 แถว ผลขึ้นกับที่ว่างในแต่ละหน้าของตาราง
จึงยังสรุปไม่ได้ว่าบนเครื่องจริงเป็นแบบใด ถ้าเป็นจริง ไฟล์ `pg_dump` จะเรียงผู้ใช้ตามลำดับโหวตด้วย ซึ่งขัดกับคู่มือ §3.1
ต้องตรวจเพิ่มด้วยการนำเข้ารายชื่อด้วย `import-students` จริง ให้ผู้ใช้เข้าระบบก่อนโหวตเหมือนของจริง แล้วเทียบลำดับในไฟล์ `pg_dump`

<a id="s2"></a>
**S2 แถวรุ่นเก่าและ WAL ของ PostgreSQL เก็บประวัติครบทุกการโหวต** ทุกครั้งที่มีการโหวต แถวคะแนนของพรรคถูกเขียนรุ่นใหม่ด้วยเลข transaction เดียวกับแถวผู้ใช้
รุ่นเก่ายังอยู่ในไฟล์ข้อมูลจนกว่า `VACUUM` จะเก็บ และอยู่ใน WAL superuser จึงน่าจะกู้ได้ว่าใครเลือกอะไรครบทุกคนโดยไม่ต้องใช้กุญแจ
ต้องตรวจเพิ่มด้วยส่วนขยาย `pageinspect` และ `pg_waldump` ซึ่งชุด PostgreSQL ที่ใช้ทดสอบไม่มี

<a id="s3"></a>
**S3 การจับคู่ข้อมูลจาก PSU SSO** รหัสนักศึกษามาจากช่อง `StudentID` และถ้าไม่มีจะใช้ `preferred_username` หรือ `sub` แทน (`src/lib/auth.js` บรรทัด 123)
ถ้า SSO ส่งค่าในช่องสำรองไม่ตรงกับรหัสในรายชื่อ ผู้มีสิทธิ์จะโหวตไม่ได้ ต้องตรวจกับ SSO จริง

โค้ดกันไว้ด้วยการไม่รับรหัสกลางสำหรับ STAFF ผลที่คาดคือบัญชีนั้นเข้าหน้าแอดมินไม่ได้ ไม่ใช่ได้สิทธิ์เพิ่ม แต่ยังไม่ได้รันพิสูจน์

<a id="s4"></a>
**S4 ตัวจำกัดการเดารหัสผ่านพึ่ง nginx** เมื่อส่งคำขอตรงเข้าพอร์ตของแอปพร้อมเปลี่ยนค่า `X-Forwarded-For` ทุกครั้ง ไม่ถูกจำกัดเลย (12 ครั้งได้ 401 ทั้งหมด)

## สิ่งที่ตรวจแล้วพบว่าถูกต้อง

<a id="v1"></a>
**V1 หนึ่งคนหนึ่งเสียง**
- transaction การโหวต 25 รายการพร้อมกันของผู้ใช้คนเดียวบน PostgreSQL จริง สำเร็จ 1 ถูกปฏิเสธ 24 ไม่มี error
- คำขอ `POST /api/vote` 20 รายการพร้อมกันจาก session เดียว ได้ 200 หนึ่งครั้ง ที่เหลือ 403 ALREADY_VOTED 14 ครั้ง และ 429 จากตัวจำกัดความถี่ 5 ครั้ง จำนวนบัตรเพิ่ม 1 ใบ
- ผู้โหวต 120 คนพร้อมกัน สำเร็จ 120 โซ่ต่อเนื่องไม่มีช่องว่าง จำนวนบัตร ผู้ใช้สิทธิ์ และคะแนนรวมเท่ากัน
- `studentId` ในเนื้อคำขอถูกเพิกเฉย ระบบใช้ตัวตนจาก session เท่านั้น
- การยึดสิทธิ์ ลงบัตร และบวกคะแนนอยู่ใน transaction เดียว ถ้าเซิร์ฟเวอร์หรือฐานข้อมูลล่มกลางคันจะไม่เหลือสถานะครึ่งเดียว (ตรวจจากโค้ดและจากยอดที่ตรงกันหลังการทดสอบพร้อมกัน)

<a id="v3"></a>
**V3 การเข้ารหัสและกุญแจ** บัตรเข้ารหัสด้วย RSA-OAEP 2048 บิตพร้อม nonce ไม่มีโค้ดใดใน `src/` อ่าน private key หรือเรียกฟังก์ชันถอดรหัส (ตรวจด้วย grep)
`/api/vote` ตอบ 503 ก่อนเขียนฐานข้อมูลถ้าขาด public key หรือ chain secret (ตรวจจากโค้ดบรรทัด 112-121 ไม่ได้รัน)
ไฟล์กุญแจส่วนตัวเข้ารหัสด้วย AES-256-GCM และ scrypt ส่วนว่ากุญแจไม่อยู่บนเครื่องจริงนั้นตรวจจากที่นี่ไม่ได้

<a id="v4"></a>
**V4 สิ่งที่โซ่จับได้จริง** ผู้ที่เขียนฐานข้อมูลได้แต่ไม่มี chain secret ถูกจับในทุกกรณีต่อไปนี้ (รันกับโค้ดตรวจตัวจริง)
แก้เนื้อบัตรหนึ่งใบ ลบบัตรกลางหีบ สลับเนื้อบัตรสองใบ สลับลำดับ แทรกบัตรใหม่ และเขียนทับ `ChainHead` อย่างเดียว

<a id="v5"></a>
**V5 การปิดคะแนน** ขณะมีคะแนนจริงในหีบและยังไม่เปิดผล ส่งคำขอ 24 รายการไปยัง endpoint และหน้าเว็บทั้งหมดในฐานะคนนอก นักศึกษา และแอดมิน
ไม่มีรายการใดคืนคะแนนที่ไม่ใช่ศูนย์ รวมถึงหน้าแอดมินและ response ของการแก้ข้อมูลพรรค ลำดับพรรคก่อนเปิดผลเรียงตามหมายเลข ไม่เรียงตามคะแนน
สิ่งที่เปิดเผยโดยตั้งใจคือจำนวนผู้ใช้สิทธิ์รวมแบบสดต่อสาธารณะ และจำนวนผู้ใช้สิทธิ์แยกชั้นปี สาขา เพศแบบสดต่อแอดมิน

<a id="v6"></a>
**V6 สิทธิ์แอดมิน** ทุก endpoint ของแอดมินตอบ 401 เมื่อไม่มี cookie (ยกเว้น `GET /api/admin/page-layout` ที่ตั้งใจเปิดเพราะมีแค่ธีมและ layout)
session ของ PSU SSO ของผู้ที่เป็นแอดมินไม่ให้สิทธิ์ใด (401) token ที่ลายเซ็นถูกแก้ถูกปฏิเสธ การถอน `isAdmin` มีผลกับคำขอถัดไปทันที
รหัสผิดและบัญชีที่ไม่ใช่แอดมินได้ 401 เหมือนกัน cookie เป็น httpOnly และ SameSite=Strict
ไม่มี API ใดลบบัตรหรือรีเซ็ตคะแนน เครื่องมือทดสอบตอบ 404 เมื่อไม่ได้เปิดสวิตช์ การเปลี่ยนหมายเลขพรรคและลบพรรคหลังมีบัตรถูกปฏิเสธ (409)
การรับรองผลตรวจ role STAFF และตรวจโซ่ใน transaction เดียวกับการตั้งธง (ตรวจจากโค้ด)

<a id="v7"></a>
**V7 สิทธิ์ผู้ลงคะแนน** ผู้ที่ไม่มี session ได้ 401 ผู้ที่ชั้นปีไม่อยู่ในปี 1 ถึง 4 ได้ 403 ตัวเลือกที่ไม่มีอยู่ได้ 400
ผู้ที่เข้าผ่าน SSO แต่ไม่อยู่ในรายชื่อนำเข้าจะไม่มีชั้นปีและโหวตไม่ได้ (ตรวจจากโค้ด) mock login ถูกลงทะเบียนเฉพาะเมื่อ `NODE_ENV` ไม่ใช่ production
หรือเมื่อตั้ง `E2E_MOCK_LOGIN=true` พร้อมกับชื่อฐานข้อมูลลงท้าย `_e2e` ยืนยันบน production build แล้วว่า `/api/auth/providers` มีเพียง `authentik` และข้อตรวจความพร้อมเรื่องนี้ขึ้นผ่าน (`check-admin-upload-prod.mjs`)

<a id="v8"></a>
**V8 CSRF การอัปโหลด และ URL** คำขอข้ามเว็บห้ารูปแบบ (Origin ต่างโดเมนใต้ psu.ac.th, same-site, cross-site, Origin เป็น null, โดเมนที่ขึ้นต้นเหมือน)
ถูกปฏิเสธ 403 ทั้งที่ `/api/vote` และ `/api/admin/dashboard` ผู้ถูกโจมตีไม่ถูกบันทึกว่าโหวต คำขอที่ Content-Type ไม่ใช่ JSON ถูกปฏิเสธ
รูปที่อัปโหลดถูกตรวจชนิดจากไบต์จริง รับเฉพาะ JPG PNG WebP และถูกเข้ารหัสใหม่ก่อนเก็บ ชื่อไฟล์และโฟลเดอร์ถูกกรองอักขระ
ลิงก์แบบประเมินรับเฉพาะ Google Forms ลิงก์โซเชียลรับเฉพาะ http และ https (สามข้อหลังตรวจจากโค้ด)

## เรื่องที่ README ไม่ได้พูดถึง

**เซิร์ฟเวอร์ล่มกลางการโหวต** คะแนนไม่เสียหายเพราะแต่ละการโหวตเป็น transaction เดียว ผู้ที่กดแล้วไม่ได้รับคำตอบตรวจสถานะของตนเองได้จากหน้าเว็บ
ความเสี่ยงอยู่ที่การกู้คืนมากกว่า ดู F3

**การกู้คืนจากข้อมูลสำรอง** ชุดสำรองทุก 6 ชั่วโมงหมายความว่าการกู้ระหว่างเปิดหีบอาจเสียบัตรสูงสุด 6 ชั่วโมงโดยไม่มีสิ่งใดแจ้ง
คู่มือมีขั้นตอนกู้ แต่ไม่มีขั้นตอนสำหรับกรณีกู้ระหว่างเปิดหีบ และไม่มีการเทียบกับปลายโซ่ที่ส่งออกไว้
ชุดสำรองยังมีรายชื่อผู้ใช้สิทธิ์และคะแนน ณ เวลานั้น จึงเกี่ยวกับความลับตาม F5 เส้น E

**ขั้นตอนที่คนต้องทำด้วยมือ และผลถ้าไม่ทำ**

| ขั้นตอน | ถ้าข้าม |
|---|---|
| ลง `ballot-grants.sql` บนเครื่องจริง | บัญชีของเว็บลบและแก้บัตรกับ audit log ได้ |
| ตั้ง cron `export-chain-head.js` และเก็บไฟล์ไว้เครื่องอื่น | ไม่มีทางจับ F3 |
| เทียบปลายโซ่ที่ส่งออกกับฐานข้อมูลด้วยตา | ไม่มีเครื่องมือทำให้ |
| ถอดบัตรนับใหม่ด้วย private key | ไม่มีทางจับ F1 ปัจจุบันทำเฉพาะเมื่อมีข้อพิพาท |
| เก็บสำเนา "ตัวเลขที่รับรองไว้" นอกระบบ | ผู้ที่แก้ฐานข้อมูลได้แก้ค่าที่รับรองไว้ให้ตรงกันได้ |
| รัน `CLUSTER` ตารางผู้ใช้หลังรับรองผล | เกี่ยวกับ S1 |
| ทำลายกุญแจและชุดสำรองพร้อมกันเมื่อขึ้นปีใหม่ | ความเสี่ยงด้านความลับสะสมข้ามปี |

**ผู้ถือกุญแจ** คู่มือระบุเองว่าปัจจุบันเจ้าหน้าที่ IT คนเดียวถือทั้งไฟล์กุญแจ รหัสผ่าน และสิทธิ์ฐานข้อมูล
บุคคลนี้จึงทำ F1 ถึง F3 ได้และรู้ตัวเลือกของผู้ลงคะแนนได้ ระบบตั้งอยู่บนความไว้ใจในบุคคลนี้ องค์กรที่จะนำไปใช้ควรตัดสินใจเรื่องนี้อย่างรู้ตัว

## สิ่งที่ไม่ได้ตรวจ หรือตรวจจากในเครื่องไม่ได้

- การตั้งค่า nginx, TLS, การผูกพอร์ต, firewall และค่า `.env` ของเครื่องจริง
- ว่าเครื่องจริงลง `ballot-grants.sql` แล้วหรือไม่ และบัญชีฐานข้อมูลใดมีสิทธิ์อะไร
- ว่า private key ไม่อยู่บนเซิร์ฟเวอร์จริง และมีผู้ถือกี่คน
- PSU SSO ของจริง (ค่าที่ส่งกลับ กลุ่มผู้ใช้ การออกจากระบบ)
- พฤติกรรมของ production build ส่วนใหญ่ (HSTS, CSP) การทดสอบ HTTP ของข้อค้นพบใช้ `next dev` ส่วนที่ยืนยันบน production build แล้วคือ mock login ปิด, cookie แอดมินเป็น Secure/HttpOnly/SameSite=strict และการอัปโหลดรูป
- `scripts/backup.sh`, `restore.sh`, `setup.sh` และ Docker ไม่ได้รัน เพราะเครื่องนี้ไม่มี `pg_dump`, `psql` และ Docker
- `import-students.js`, `archive-year.js`, `preflight-year.js`, `generate-election-keys.js`, `admin.js` อ่านเพียงบางส่วน ไม่ได้รัน
- `npm run e2e` และ `election.test.mjs` ไม่ได้รัน ส่วน `npm run build` ผ่าน และ unit test ใน `scripts/smoke` ผ่าน 250 จาก 250
- การฉีดสคริปต์หรือ CSS ผ่านธีมและข้อความที่แอดมินกรอก (อ่าน CSP และตัวกรองแล้ว แต่ไม่ได้ทดสอบเจาะ)
- ช่องโหว่ของ dependency (`npm audit`) และการทดสอบโหลด
- การกู้ประวัติจากแถวรุ่นเก่าและ WAL (S2)

## วิธีรันซ้ำ

สคริปต์ทั้งหมดอยู่ใน `scripts/audit/` สคริปต์ที่ใช้ฐานข้อมูลจะปฏิเสธการทำงานถ้า `AUDIT_DATABASE_URL` ไม่ได้ชี้เครื่องตัวเอง
หรือชื่อฐานข้อมูลไม่ลงท้าย `_e2e` หรือ `_test` และไม่อ่าน `DATABASE_URL` จาก `.env`

ไม่ต้องใช้ฐานข้อมูล

```bash
node scripts/audit/repro-01-verifier-blind-spots.cjs     # F1 F2 F3 และ V4
node scripts/audit/repro-02-embargo-peek.mjs             # F4
node scripts/audit/repro-03-audit-log-coverage.mjs       # F7
```

ใช้ PostgreSQL ในเครื่อง (สร้างฐานข้อมูลเปล่าแบบ UTF8 ชื่อลงท้าย `_e2e` ก่อน)

```bash
export AUDIT_DATABASE_URL="postgresql://<ผู้ใช้>:<รหัส>@127.0.0.1:<พอร์ต>/fms_audit_e2e"
DATABASE_URL="$AUDIT_DATABASE_URL" npx prisma db push --skip-generate
AUDIT_ROSTER=2000 AUDIT_TURNOUT=800 node scripts/audit/repro-db-01-voter-linkage.cjs   # F5 S1
node scripts/audit/repro-db-02-real-tools-on-tampered-db.cjs                            # F1 F3 V1
```

ใช้แอปจริง (เปิดเซิร์ฟเวอร์ในหน้าต่างหนึ่ง แล้วรันสคริปต์ในอีกหน้าต่าง)

```bash
node scripts/audit/start-audit-server.cjs                # next dev พอร์ต 3210 ชี้ฐานข้อมูลทดสอบ
node scripts/audit/repro-http-01-live-app.mjs            # V1 V5 V6 V7 V8 F4 F6 F7 F8 F9 S4
```

ตรวจการอัปโหลดรูปจากหน้าแอดมินบน production build (ต้อง `npm run build` ก่อน)

```bash
node scripts/audit/check-admin-upload-prod.mjs           # อัปโหลดทุกชนิด + สิ่งที่ต้องถูกปฏิเสธ 25 ข้อ
```

หมายเหตุสำหรับผู้รันซ้ำ: ข้อ 10 ของสคริปต์ HTTP เรียก `/api/debug-db` ซึ่งคอมไพล์ไม่ผ่าน และทำให้ `next dev` ตอบ 500 กับคำขอถัดไปจนกว่าจะรีสตาร์ต
สคริปต์จึงเรียกข้อนี้เป็นลำดับท้าย ถ้าลบไฟล์นั้นแล้วข้อนี้จะตอบ 404

ไฟล์ที่เปลี่ยนใน branch นี้: เพิ่ม `scripts/audit/` และรายงานฉบับนี้ และเพิ่มรายการ `fms-audit` ใน `.claude/launch.json` ไม่มีการแก้ไฟล์ใน `src/`
